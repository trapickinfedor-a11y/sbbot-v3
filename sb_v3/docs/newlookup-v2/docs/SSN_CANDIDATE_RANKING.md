# Алгоритм: найти нужного человека среди сотен строк SSN (старые адреса)

Когда **`firstname` + `lastname` + `st`** даёт десятки/сотни записей (например Thomas Dickson PA → 458, Stephen Rudolph PA → 66), цель — **выбрать одну (или несколько кандидатов на ручной выбор)** полную строку с SSN.

Ниже — практичный **двухфазный** алгоритм: сначала **собрать кандидатов** (с учётом старых адресов), потом **ранжировать** локально.

---

## Входные данные (что хранить в заказе / парсере)

- **Имя:** `first`, `middle` (или инициал), `last`, `suffix` (JR, III, …) — если есть.
- **Список адресов `addresses[]`** — не один «текущий», а **все известные из fullz** (текущий первым, остальные по убыванию уверенности / даты, если есть).
  - Каждый: `street`, `city`, `st`, `zip` (и при наличии `zip4`, `county`).
- **Опционально:** `dob` (полная или год), `phone`, `email` — сильно режут неоднозначность.

---

## Фаза 1 — сбор кандидатов (API-запросы)

**Идея:** не полагаться на один zip — человек в базе может быть по **старому** адресу.

1. **Базовый узкий запрос** (если есть «лучший» адрес):  
   `firstname`, `lastname`, `st`, **`zip`** (и при необходимости `city`).  
   → часто 0–5 записей; если **0** — не значит «нет в базе», значит **в файле другой zip**.

2. **Расширение по всем известным ZIP:**  
   Для каждого уникального `zip` из `addresses[]` выполнить тот же поиск (имя + штат + zip).  
   Объединить ответы по стабильному ключу записи (`id` у USFULL или `ssn`+`dob` у себя), **дедупликация**.

3. **Страховка по штату (широкий):**  
   Если после п.1–2 кандидатов мало или 0 — один запрос **`firstname` + `lastname` + `st`** (как сейчас), получить до лимита API (у USFULL до ~1000 строк).  
   Использовать только как **источник для ранжирования**, не как финальный ответ без скоринга.

4. **Ограничение объёма:**  
   Если широкий запрос возвращает сотни строк — **всё равно ранжировать все** на клиенте (458 — ок), но **не автоматом брать первую строку**.

---

## Фаза 2 — нормализация и скоринг (локально)

### Нормализация текста

- Верхний регистр, схлопнуть пробелы.
- **Адрес:** выделить **номер дома** и **остаток улицы** отдельно; унифицировать типы: `ST`/`STREET`, `DR`/`DRIVE`, `N`/`NORTH` и т.д. (правила USPS или простая таблица синонимов).
- **ZIP:** только первые 5 цифр для сравнения; `zip4` — бонус при совпадении.
- **Имя:** middle — сравнивать **первую букву** и полное middle (если есть).

### Веса (пример — подкрутить по статистике)

| Сигнал | Баллы (пример) |
|--------|----------------|
| Совпадение **полного нормализованного street + zip** с любым из `addresses[]` | **100** |
| Совпадение **номера дома + фамилия улицы** (fuzzy) + тот же **zip** | **90** |
| Тот же **zip**, улица похожа (Levenshtein ≤ 1–2 на токенах) | **70** |
| Тот же **city** + **st**, другой zip из списка адресов | **50** |
| Тот же **city** (нормализованный), zip не из списка | **25** |
| Только **st** + имя совпало | **5** |

Дополнительные **бонусы** (к сумме или отдельный множитель):

- **Middle:** полное совпадение +20; совпадение инициала +10; явный конфликт (C vs B) **−40**.
- **Suffix** (JR/SR/III): совпадение +15, конфликт −30.
- **DOB:** полное совпадение +50; совпадение только года +20; конфликт −∞ (исключить кандидата).
- **Телефон:** нормализовать до 10 цифр, совпадение +40 (если в записи есть phone).

**Итог по кандидату:**  
`score = max_over_addresses( address_match_score ) + name_bonuses + dob_bonus + phone_bonus`

Брать **`max` по адресам`**, потому что в базе может быть **старый** адрес — он должен дать высокий балл, если этот старый адрес есть в `addresses[]`.

---

## Решение: авто vs ручное

1. Отсортировать кандидатов по `score` по убыванию.
2. **Авто-принятие** только если:
   - `score[1] - score[2] >= margin` (например **25**), и  
   - `score[1] >= min_threshold` (например **80**), и  
   - нет жёсткого конфликта по DOB/middle/suffix.
3. Иначе — отдать оператору **топ-3** с полями: score, matched_signal («zip+street», «old address from list #2», …), урезанный вывод SSN (последние 4) до подтверждения.

---

## Псевдокод

```
candidates = {}

for zip in unique_zips(addresses):
    candidates.merge( api_search(first, last, st, zip=zip) )

if len(candidates) == 0 or need_fallback:
    candidates.merge( api_search(first, last, st) )  # широкий

for row in candidates.unique():
    row.score = 0
    for addr in addresses:
        row.score = max(row.score, match_address(row, addr))
    row.score += match_middle(row, order)
    row.score += match_dob(row, order)
    row.score += match_phone(row, order)

return rank_and_decide(candidates)
```

## Интеграция с ботом / `UsfullClient`

1. Парсер fullz складывает **массив адресов**, не одну строку.
2. После `search_ssn` с сырым `results` вызывается **локальный ранкер** (Python-функция в `shared/` или `mirror_bot/services/`), который возвращает `best` / `top_n` / `ambiguous`.
3. Логировать **почему** выбран кандидат (аудит, споры по заказам).

---

## Риски

- **Однофамильцы** с тем же zip — остаётся неоднозначность; без DOB/phone **не** выдавать SSN автоматически.
- **Ошибки в исходном fullz** (опечатка в номере дома) — помогает fuzzy по улице и список из нескольких адресов.
- **Соответствие законодательству** — автоматический выбор PII только при явной политике и порогах; иначе только ручной выбор.

---

## Кратко

1. Искать **по каждому известному ZIP** + имя + штат, мержить.  
2. Если пусто — широкий **имя + штат**, потом **скорить** против **всех** известных адресов (max по адресам).  
3. Усилить **middle, suffix, DOB, phone**.  
4. Авто только при **большом зазоре** между 1-м и 2-м местом; иначе — топ-3 на ручной выбор.
