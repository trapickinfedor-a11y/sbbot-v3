## 1. Введение

### 1.1. Назначение

Настоящий документ (SRS) определяет функциональные и нефункциональные требования к программному комплексу **Newlookup v9**. Система представляет собой мульти-агентную платформу для предоставления цифровых товаров и услуг, построенную вокруг Telegram-ботов и централизованной веб-панели управления.

### 1.2. Руководящие принципы

Разработка и эксплуатация системы должны основываться на следующих принципах:

1.  **Надёжность:** Система должна работать стабильно 24/7, минимизируя время простоя.
2.  **Безопасность:** Все данные пользователей, транзакции и внутренние процессы должны быть защищены от несанкционированного доступа.
3.  **Масштабируемость:** Архитектура должна позволять горизонтальное масштабирование для обработки растущего числа пользователей и заказов.
4.  **Модульность:** Компоненты системы должны быть независимыми, что упрощает их разработку, тестирование и обновление.
5.  **Удобство использования:** Интерфейсы для всех ролей (покупатели, продавцы, администраторы) должны быть интуитивно понятными.

### 1.3. Область действия

Документ охватывает все компоненты системы, включая:

*   **Telegram-боты:** Mirror Bot, Seller Bot, Main Bot, Marketer Bot, Support Bot.
*   **Веб-панель:** Admin Panel для управления всей системой.
*   **База данных:** Структура и взаимодействие с данными.
*   **Интеграции:** Внешние платёжные системы и сервисы.

## 2. Архитектура системы

### 2.1. Компоненты

Система состоит из следующих независимых, но взаимосвязанных сервисов (агентов):

| Компонент | Описание |
| :--- | :--- |
| **Shared** | Общий слой с моделями SQLAlchemy, сервисами, утилитами и настройками. Используется всеми остальными компонентами. |
| **Mirror Bot** | Основной интерфейс для **покупателей**. Через него происходят все покупки, общение с поддержкой и управление профилем. |
| **Seller Bot** | Интерфейс для **продавцов**. Позволяет управлять товарами, отслеживать продажи, выводить средства и общаться с покупателями. |
| **Main Bot** | Интерфейс для **владельцев ботов**. Позволяет создавать зеркала Mirror Bot, отслеживать доход и статистику. |
| **Marketer Bot** | Интерфейс для **партнёров (маркетологов)**. Позволяет создавать ботов для привлечения пользователей и отслеживать доход от их пополнений. |
| **Support Bot** | Интерфейс для **команды поддержки**. Включает роли `support` (тикеты), `finance` (финансовые операции) и `uploader` (загрузка товаров). |
| **Admin Panel** | Центральная **веб-панель** для администраторов. Предоставляет полный контроль над системой: пользователи, товары, цены, роли, финансы. |
| **Seller Mini App** | Веб-приложение (Mini App) внутри Telegram для продавцов, предоставляющее расширенный интерфейс для управления товарами и настройками. |

### 2.2. Технологический стек

| Категория | Технология |
| :--- | :--- |
| **Язык программирования** | Python 3.11+ |

| **Веб-фреймворк** | FastAPI |

Ключевые переменные, необходимые для конфигурации системы:

## 4. Mirror Bot (Покупатель)

### 4.1. Главное меню

REQ-MB-001: Главное меню ДОЛЖНО быть динамическим и управляться из Admin Panel через таблицу `mirror_menu_categories`.
REQ-MB-002: Администратор МОЖЕТ добавлять, редактировать, скрывать и менять порядок категорий.

### 4.2. Профиль пользователя

REQ-MB-003: В профиле ДОЛЖНЫ отображаться `user_id`, `username`, текущий баланс и язык.
REQ-MB-004: Пользователь МОЖЕТ изменить язык интерфейса.

### 4.3. Пополнение баланса

REQ-MB-005: Пользователь МОЖЕТ пополнить баланс через доступные платежные шлюзы (Crypto Bot, Helecat).

### 4.4. Раздел "Banks"

REQ-MB-006: Категории VCC, Personal, Business, Crypto ДОЛЖНЫ поддерживать 3 режима работы, настраиваемые в Admin Panel:
- **In Stocks:** Покупка готового товара от продавца (Seller Bot).
- **Per Order:** Создание заказа для воркера.
- **Per Order (Same Name/Address):** Заказ для воркера с указанием имени и адреса покупателя.

REQ-MB-007: Администратор МОЖЕТ добавлять новые подкатегории и привязывать к ним воркеров.

### 4.5. Раздел "Brute Bank"

REQ-MB-008: Покупатель видит список доступных банков в формате `BankName [атрибуты] [кол-во]`, например, `Chase [AN:RN+YODLEE] [150]`.
REQ-MB-009: При выборе банка покупатель видит цену за один аккаунт и может совершить покупку.
REQ-MB-010: После покупки одна строка из файла аккаунтов списывается и доставляется покупателю в чат.

### 4.6. Раздел "Accounts"

REQ-MB-011: Раздел должен содержать 2 категории: **Proxy** и **AI**.
REQ-MB-012: Товары в этих категориях (например, `ChatGPT Plus`, `Midjourney Pro`) управляются из Admin Panel (таблицы `account_categories` и `account_items`).
REQ-MB-013: Интерфейс должен поддерживать пагинацию для просмотра большого количества товаров.

### 4.7. Раздел "eSIM"

REQ-MB-014: Раздел должен предлагать 2 типа eSIM: **SMS** и **Data**.
- **SMS:** Выбор оператора (Verizon, AT&T, T-Mobile) и периода (1, 3, 6 месяцев).
- **Data:** Выбор объёма трафика (5, 10, 15 ГБ).
REQ-MB-015: Цены на все комбинации eSIM управляются из Admin Panel.

### 4.8. Мои заказы и чаты

REQ-MB-016: В разделе "Мои заказы" покупатель видит историю всех своих покупок.
REQ-MB-017: Для заказов, выполненных продавцами, у покупателя есть кнопка **"Написать продавцу"**.
REQ-MB-018: Чат с продавцом доступен до и после подтверждения получения товара.
- **Сценарий 1 (Спор):** Если покупатель не подтверждает заказ и открывает спор, чат остаётся активным для общения с продавцом и модератором.
- **Сценарий 2 (Вопрос):** Если покупатель подтвердил заказ, но у него возник вопрос, он может снова написать продавцу через этот чат.

### 4.9. Гарантии и получение товара

REQ-MB-019: При покупке товара, хранящегося в S3 (Logs, Brute, Selfreg), покупатель сначала видит предупреждающее сообщение о гарантиях.
REQ-MB-020: После согласия с условиями покупатель нажимает кнопку **"Открыть товар"** и получает временную ссылку на скачивание файла из S3.

## 5. Seller Bot (Продавец)

### 5.1. Депозит и доступ

REQ-SELL-001: Для получения доступа к загрузке товаров продавец ДОЛЖЕН внести залоговый депозит.
REQ-SELL-002: Размер депозита определяет доступные для загрузки категории товаров:

| Депозит | Доступные категории |
| :--- | :--- |
| $150 | CHECKS, Selfreg BA |
| $200 | Enroll (Debit/Credit), NFC, OTP |
| $300 | CC (with zip, with fullz, non-vbv), Brute, Logs BA |
| $600 | Все категории |

### 5.2. Загрузка товаров (Конфигураторы)

REQ-SELL-003: Для каждого типа товара должен быть свой конфигуратор загрузки.

#### 5.2.1. Brute Bank

REQ-SELL-004: Продавец выбирает категорию (банк), к которой он хочет загрузить аккаунты (например, `Chase [AN:RN+YODLEE]`).
REQ-SELL-005: Продавец загружает `.txt` файл, где каждая строка — это один аккаунт в формате, соответствующем категории.
REQ-SELL-006: Продавец устанавливает цену за одну строку.

#### 5.2.2. Logs BA

REQ-SELL-007: Продавец заполняет поля в конфигураторе:
- Список банков (название, тип счёта, баланс)
- Тип и статус почты
- Флаги (CVV, инвестиции, Zelle и т.д.)
- Цена лота
REQ-SELL-008: Продавец загружает `.zip` файл с логами.

#### 5.2.3. Selfreg BA / Selfreg CC

REQ-SELL-009: Продавец заполняет подробный конфигуратор для Selfreg, включающий:
- **Selfreg BA:** Банк, баланс, доступ к телефону/почте, наличие SSN/Docs, тип интеграции.
- **Selfreg CC:** Банк, кредитный лимит, доступ к телефону/почте, штат/ZIP, тип карты.
REQ-SELL-010: Продавец загружает файл с данными.

#### 5.2.4. CC (массовая загрузка)

REQ-SELL-011: Продавец выбирает подтип (with_fullz, zip_only, non_vbv).
REQ-SELL-012: Продавец загружает `.txt` файл, где каждая строка — одна карта в соответствующем формате.

#### 5.2.5. OTP / NFC / Enroll

REQ-SELL-013: Продавец заполняет описание и характеристики товара **полностью сам** и загружает файл.

### 5.3. Уведомления

REQ-SELL-014: Продавец МОЖЕТ настраивать получение уведомлений в **Seller Mini App**.
REQ-SELL-015: Доступные для настройки уведомления:
- Покупка его товара (обычного или из Brute Bank)
- Товар успешно прошёл модерацию и загружен
- Товар отправлен на модерацию
- Товар автоматически снят с продажи таймером
- Ежедневный отчёт (загружено/продано/заработано)
- Сообщения от поддержки о действиях с его товарами
- Новые сообщения в спорах по его заказам
- Изменение статуса заявки на вывод средств

## 6. Main Bot (Владелец ботов)

REQ-MAIN-001: Функционал Main Bot остаётся без изменений. Он используется для управления собственными ботами (зеркалами).
REQ-MAIN-002: Вывод средств для владельцев ботов должен использовать общую таблицу `withdrawal_requests` и обрабатываться ролью `finance` в Support Bot.

## 7. Marketer Bot (Партнёр)

### 7.1. Реферальная система

REQ-MARK-001: Marketer Bot позволяет партнёру создать собственного Telegram-бота для привлечения пользователей.
REQ-MARK-002: Когда пользователь регистрируется в Mirror Bot через бота-посредника, в его запись в таблице `users` в поле `marketer_id` записывается ID партнёра.
REQ-MARK-003: Партнёр получает **8.5%** с каждого пополнения баланса привлечённых им пользователей.

### 7.2. Защита от злоупотреблений

REQ-MARK-004: В Marketer Bot должно быть встроено предупреждение о недопустимости злоупотребления реферальной системой.
- **Текст предупреждения:** "Наша система использует AI-алгоритмы для обнаружения мошеннических схем и аффилированных регистраций. При обнаружении подозрительной активности, когда более 30% привлечённых пользователей являются вашими аффилированными аккаунтами, ваш аккаунт партнёра будет заблокирован без возможности вывода средств."

## 8. Support Bot (Поддержка)

### 8.1. Роли

REQ-SUP-001: Support Bot должен поддерживать следующие роли, управляемые из Admin Panel:

| Роль | Описание |
| :--- | :--- |
| `finance` | Обрабатывает заявки на вывод, видит финансовую статистику. |
| `support` | Отвечает на тикеты пользователей, участвует в спорах. |
| `moderator` | Модерирует товары продавцов, может менять баланс пользователей с указанием причины. |
| `uploader` | Загружает товары в каталог от имени платформы. |

### 8.2. Роль `finance`

REQ-SUP-002: `finance` видит все заявки из таблицы `withdrawal_requests` и может их одобрить или отклонить.

### 8.3. Роль `moderator`

REQ-SUP-003: `moderator` может изменять баланс любого пользователя, но при этом **обязан** указать причину изменения. Это действие логируется.

### 8.4. Роль `uploader`

REQ-SUP-004: Роли `uploader` можно назначить права на загрузку товаров только в определённые каталоги (Banks, CC, Brute, Logs, Accounts, eSIM и т.д.).
REQ-SUP-005: `uploader` получает в Support Bot **полный лог действий** по назначенным ему каталогам (кто, что и когда создал, изменил или удалил в Admin Panel).

## 9. Admin Panel (Веб-панель)

### 9.1. Дизайн и общие требования

REQ-ADM-001: Дизайн должен быть выполнен в тёмной теме, с плотным расположением элементов, без микролагов и с адаптивностью для десктопов и ноутбуков.
REQ-ADM-002: Все таблицы должны поддерживать пагинацию, сортировку и поиск.

### 9.2. Управление каталогом

REQ-ADM-003: Администратор МОЖЕТ управлять категориями главного меню Mirror Bot (таблица `mirror_menu_categories`).
REQ-ADM-004: Администратор МОЖЕТ управлять ценами на все услуги (таблица `service_prices`).
REQ-ADM-005: При добавлении новой подкатегории в раздел, управляемый воркерами (например, новый тип VCC), администратор должен иметь возможность **сразу привязать к ней воркера**.

### 9.3. Управление купонами

REQ-ADM-006: Администратор (super_admin/admin) МОЖЕТ создавать и управлять скидочными купонами.
REQ-ADM-007: Параметры купона:
- Время действия
- Максимальное количество активаций
- Привязка к конкретной услуге/категории/подкатегории
- Фиксированная цена или скидка в %

### 9.4. Рассылки

REQ-ADM-008: Рассылки должны поддерживать 4 языка (EN, RU, ES, ZH) с отдельными полями для каждого языка и автоматическим fallback на английский, если перевод отсутствует.
REQ-ADM-009: Должна быть возможность отложенной публикации по московскому времени.

## 12. Глоссарий

| Термин | Описание |
| :--- | :--- |
| **Brute Bank** | Категория товаров, представляющих собой аккаунты, полученные методом перебора. Продаются мгновенно. |
