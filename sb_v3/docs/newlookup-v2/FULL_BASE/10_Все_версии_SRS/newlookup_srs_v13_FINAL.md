## 1. Философия и Стратегия

Newlookup — это не просто маркетплейс, а **экосистема для роста**. Вся архитектура и логика подчинены одной цели: **масштабирование через партнёров**. Система спроектирована так, чтобы каждый участник — продавец, маркетолог, воркер — был мотивирован привлекать новых пользователей и увеличивать оборот.

**Ключевые принципы системы:**

| Принцип | Описание |
| --- | --- |
| **Всё есть API** | Любой элемент системы (пользователь, товар, заказ) доступен через внутренний API, что позволяет легко добавлять новые интерфейсы. |
| **Единый источник правды** | База данных PostgreSQL — единственный источник достоверной информации. Никакой логики в кэше или файлах. |
| **Асинхронность** | Вся система построена на асинхронных операциях для высокой производительности. |
| **Zero Trust** | Все действия, влияющие на финансы или данные, проходят через несколько уровней проверки и логируются в `audit_logs`. |
| **Рост через делегирование** | Система поощряет создание команд (продавцы + помощники, маркетологи + боты-прокси). |
| **Многоязычность** | Система поддерживает 4 языка: EN, RU, ES, ZH. |

## 3. Ролевая Модель (RBAC )

Система имеет 7 ключевых ролей, каждая со своими правами и интерфейсами.

| Роль | Основной интерфейс | Ключевая задача |
| --- | --- | --- |
| **Пользователь** | Mirror Bot | Покупка товаров и услуг. |
| **Продавец** | Seller Bot, Seller Mini App | Продажа товаров, управление командой. |
| **Помощник продавца** | Seller Bot | Помощь продавцу (загрузка товаров, поддержка). |
| **Маркетолог** | Marketer Bot | Привлечение пользователей через ботов-прокси. |
| **Воркер** | Worker Bot | Выполнение заказов Per Order. |
| **Сотрудник поддержки** | Support Bot, Admin Panel | Модерация, споры, финансовые операции. |
| **Владелец** | Main Bot, Admin Panel | Стратегическое управление, аналитика. |

### 3.1. Права сотрудников поддержки

| Роль | Права |
| --- | --- |
| `L1 Support` | Отвечать на тикеты, просматривать заказы. Нет доступа к финансам. |
| `L2 Support (Moderator)` | Модерировать товары, решать споры, блокировать пользователей/продавцов. |
| `Finance` | Обрабатывать заявки на вывод, изменять баланс (с указанием причины). |
| `Uploader` | Загружать товары в каталог от имени платформы (только назначенные категории). |
| `Admin` | Полный доступ к Support Bot, управление ролями сотрудников. |
| `Auditor` | Read-only доступ ко всем логам и операциям для контроля. |
| `Super Admin` | Все права Admin + критически важные операции. |

## 5. Mirror Bot — Клиентский Бот

### 5.1. Первый запуск и регистрация

**REQ-MB-001:** При первом запуске (`/start`) пользователь обязан принять правила сервиса. Кнопка "✅ Принять правила" становится активной только после нажатия на "Читать правила".

**REQ-MB-002:** После принятия правил создаётся запись в `users` с привязкой к `mirror_bot_id` и, при наличии, к `marketer_id` (если пользователь пришёл через бота-прокси маркетолога).

**REQ-MB-003:** Если пользователь пришёл по реферальной ссылке другого пользователя (`?start=ref_XXXXX`), в его запись прописывается `referrer_id`. Реферер получает 4% с первого пополнения реферала. Бот явно сообщает: `«Вы пришли по приглашению. Вам начислен приветственный бонус!»`.

### 5.2. Главное меню

**REQ-MB-004:** Главное меню является **полностью динамическим** и управляется из Admin Panel через таблицу `mirror_menu_categories`. Администратор может добавлять, удалять, переименовывать и менять порядок категорий.

Статус наличия товаров отображается в кнопках:

| Формат кнопки | Пример | Описание |
| --- | --- | --- |
| `{иконка} {название} [{кол-во}]` | `🏦 Banks [142]` | Количество доступных товаров. |
| `{иконка} {название} [PREORDER]` | `📱 eSIM [PREORDER]` | Товар доступен для предзаказа. |
| `{иконка} {название}` | `🔍 Lookup` | Системный товар без счётчика. |

### 5.3. Профиль и Баланс

**REQ-MB-005:** Раздел "👤 Профиль" отображает: User ID, текущий баланс в USD, всего пополнено / потрачено, уровень лояльности, реферальную ссылку и количество рефералов.

Кнопки в профиле: `💳 Пополнить`, `📦 Мои заказы`, `🎟 Применить купон`, `💬 Поддержка`, `👥 Рефералы`.

**REQ-MB-006:** Пополнение баланса через BTCPay Server, Helecat, Crypto Bot (Telegram).

## 8. Marketer Bot — Бот Партнёра

### 8.1. Концепция: Боты-прокси

**REQ-MARK-001:** Маркетолог работает через систему **ботов-прокси**. Он регистрирует свой Telegram-бот в системе, и все пользователи, пришедшие через этого бота, автоматически закрепляются за ним.

**Механизм работы:**

1. Маркетолог регистрируется в Marketer Bot.

1. Нажимает "Создать бота" и вводит токен своего Telegram-бота.

1. Система сохраняет связь в `marketer_bot_links` (`marketer_id` + `mirror_bot_id`).

1. Когда новый пользователь запускает бота-прокси, в его запись в `users` прописывается `marketer_id`.

1. Маркетолог получает **8.5%** с каждого пополнения баланса привлечённых пользователей.

**REQ-MARK-002:** Маркетолог может создать до **5 ботов-прокси**.

**REQ-MARK-003 (Кастомизация):** Маркетолог может изменить приветственное сообщение бота и добавить свои кнопки в главное меню (например, ссылку на свой канал).

### 8.2. Дашборд маркетолога

**REQ-MARK-004:** Главный экран Marketer Bot показывает:

| Метрика | Описание |
| --- | --- |
| Привлечённые пользователи | Общее количество + по каждому боту-прокси. |
| Общая сумма пополнений | Суммарные пополнения привлечённых пользователей. |
| Заработано | Начислено / выплачено / доступно к выводу. |
| Конверсия | Запуски → первое пополнение (CR%). |
| ARPU | Средний доход с привлечённого пользователя. |

### 8.3. Управление ботами-прокси

**REQ-MARK-005:** В разделе "Мои боты": список всех зарегистрированных ботов с метриками по каждому, добавить новый бот (ввод токена), удалить бот (пользователи остаются привязанными к маркетологу).

### 8.4. Вывод средств

**REQ-MARK-006:** Маркетолог запрашивает вывод из Marketer Bot: выбирает метод (BTC / XMR), вводит адрес и сумму → запись в `withdrawal_requests` → уведомление роли `Finance`.

### 8.5. Антифрод-защита

**REQ-MARK-007:** В интерфейсе Marketer Bot указывается ставка **10%**, но реальная выплата — **8.5%**. Разница 1.5% удерживается на антифрод.

**REQ-MARK-008:** Предупреждение в боте:

> "Наша система использует ИИ для анализа поведения и выявления аномалий. Если более 30% ваших рефералов будут идентифицированы как аффилированные с вами аккаунты, ваш аккаунт будет заблокирован без возможности вывода средств."

**REQ-MARK-009:** Автоматическая проверка `check_fraud(marketer_id)` перед каждой заявкой на вывод:

| Условие | Действие |
| --- | --- |
| Один реферал даёт 90%+ бонусов | Заявка создаётся со статусом `blocked`, уведомление роли `Finance`. |
| 30%+ рефералов — аффилированные аккаунты | Временная заморозка, уведомление роли `Admin`. |

**REQ-MARK-010:** Уведомление маркетологу при достижении каждых 50 новых регистраций.

## 9. Support Bot — Бот Поддержки

### 9.1. Роли и права

**REQ-SUP-001:** Support Bot реализует детализированную ролевую модель (RBAC) — см. раздел 3.1.

### 9.2. Флоу: Обработка вывода средств

1. Запрос на вывод от продавца / воркера / маркетолога / владельца → уведомление роли `Finance`.

1. Уведомление содержит: кто запрашивает, сумма, метод, текущий баланс, история предыдущих выводов.

1. `Finance` нажимает "Одобрить" или "Отклонить" (с обязательным указанием причины при отклонении).

1. При одобрении — средства отправляются автоматически. Пользователь получает уведомление о статусе.

### 9.3. Флоу: Разрешение споров

1. Покупатель открывает спор → уведомление роли `Moderator`.

1. Модератор видит: историю заказа, переписку покупателя и продавца, данные товара.

1. Модератор принимает решение: вернуть покупателю / оставить продавцу / разделить сумму.

1. Решение применяется автоматически, обе стороны получают уведомление.

### 9.4. Флоу: Модерация товаров

1. При загрузке нового товара продавцом → уведомление роли `Moderator`.

1. Модератор видит карточку товара со всеми параметрами.

1. Одобрить (товар становится активным) / Отклонить (с указанием причины) / Редактировать.

1. Продавец получает уведомление о результате модерации.

### 9.5. Автоматизация рутины

**REQ-SUP-002:** Шаблоны ответов для частых вопросов. Автоматическое распределение тикетов на наименее загруженного сотрудника. SLA-таймеры: если тикет не обработан в течение N часов — эскалация на старшего сотрудника.

### 9.6. Логирование действий

## 10. Worker Bot — Бот Воркера

### 10.1. Обзор

**REQ-WRK-001:** Worker Bot — отдельный бот для исполнителей заказов (Per Order). Воркер получает уведомления о новых заказах и отправляет результаты покупателям.

### 10.2. Флоу выполнения заказа

1. Новый заказ → уведомление воркеру с деталями (тип услуги, параметры, цена).

1. Воркер может: взять в работу, отказаться (заказ уходит следующему воркеру), запросить уточнение у покупателя.

1. После выполнения воркер отправляет результат через бота.

1. Покупатель получает результат и может поставить оценку.

### 10.3. Система рейтинга воркеров

**REQ-WRK-002:** После выполнения заказа клиент оценивает работу воркера. Воркеры с высоким рейтингом получают заказы первыми.

### 10.4. Оплата воркера

**REQ-WRK-003:** Воркер получает оплату за каждый выполненный заказ (фиксированная сумма или % от цены — настраивается в Admin Panel). Деньги мгновенно переводятся с холда на основной баланс после выполнения.

**REQ-WRK-004:** Вывод средств через Worker Bot: выбор метода (BTC/XMR), ввод адреса и суммы → заявка в `withdrawal_requests` → подтверждение роли `Finance`.

## 13. Финансовая Модель и Монетизация

### 13.1. Расчёт прибыли

```
Прибыль = Цена_покупателя - Выплата_продавцу - Выплата_воркеру - Выплата_маркетологу
```

| Компонент | Значение |
| --- | --- |
| **Выплата_продавцу** | Цена продавца (без наценки системы). |
| **Выплата_воркеру** | Фикс или % от цены заказа (Per Order). |
| **Выплата_маркетологу** | 8.5% от пополнения привлечённого пользователя. |

### 13.2. Реферальная система пользователей

Пользователь получает **4%** с первого пополнения реферала. Реферальная ссылка: `https://t.me/BotName?start=ref_USERID`.

### 13.3. Система купонов

Купоны могут давать скидку на покупку товара или на пополнение баланса. Скидка применяется до списания средств. Все применения логируются в `coupon_redemptions`.

### 13.4. Программа лояльности

| Уровень | Порог трат | Бонусы |
| --- | --- | --- |
| **Bronze** | $0 | Стандартные условия. |
| **Silver** | $500 | +1% кешбэк, эксклюзивные купоны. |
| **Gold** | $2,000 | +2% кешбэк, приоритетная поддержка. |
| **Platinum** | $10,000 | +3% кешбэк, доступ к закрытым распродажам, персональный менеджер. |

### 13.5. Дополнительные потоки доходов

| Поток | Описание |
| --- | --- |
| **"Поднять в топ"** | Продавец платит за закрепление товара на первом месте в категории на 24 часа. |

| `INST MX` | Интеграция MX |
| `INST AKOYA` | Интеграция Akoya |

Список интеграций расширяемый через Admin Panel.

**Загрузка продавцом:**

1. Выбирает существующую группу или создаёт новую (через Admin Panel).

1. Загружает `.txt` файл — каждая строка один аккаунт.

1. Система парсит и добавляет каждую строку как отдельный `BruteBankItem`.

---

### 17.5. CC (Кредитные Карты от Продавцов)

Продавец сначала выбирает тип карты, затем загружает `.txt` файл. Система проверяет каждую строку по BIN (первые 6–8 цифр) и количеству полей.

| Подтип | Формат строки | Описание |
| --- | --- | --- |
| `with_fullz` | `card;exp_month;exp_year;cvv;zip;name;address;ssn;dob;phone` | Карта с полными данными. |
| `zip_only` | `card;exp_month;exp_year;cvv;zip` | Карта только с ZIP. |
| `non_vbv` | `card;exp_month;exp_year;cvv` | Карта без VBV-проверки. |

**Проверка при загрузке:**

1. Продавец выбирает тип (`with_fullz` / `zip_only` / `non_vbv`).

1. Загружает `.txt` файл.

1. Система проверяет каждую строку: соответствие формату по количеству полей.

1. BIN-проверка: первые 6–8 цифр карты сверяются с базой BIN для определения банка и типа карты (debit/credit, prepaid, страна).

1. Строки с ошибками отображаются в отчёте о загрузке.

---

### 17.6. eSIM (Ручное Управление)

Администратор в Admin Panel управляет тарифами eSIM вручную. Никакой внешней API-интеграции нет.

**Флоу после покупки:**

1. Администратор получает уведомление в Admin Panel.

1. Вручную загружает QR-код или файл активации для клиента.

1. Покупатель получает файл через Mirror Bot.

---

### 17.7. Accounts (Proxy, AI) — Предзаказ

Продажа Proxy и AI аккаунтов работает по модели **предзаказа**:

1. Покупатель выбирает тип аккаунта и оставляет заявку.

1. Заявка отображается в Admin Panel.

1. Администратор обрабатывает вручную: находит/создаёт аккаунт, загружает данные.

1. Покупатель получает данные через Mirror Bot.

Товары не хранятся в наличии — приобретаются/создаются под конкретный заказ.

## 18. Безопасность — Архитектура Недоверия (Zero Trust)

### 18.1. Защита от внешних угроз

| Мера | Описание |
| --- | --- |
| **WAF** | Перед всеми веб-интерфейсами для защиты от DDoS, SQL-инъекций, XSS. |
| **Rate Limiting** | Все API-эндпоинты и методы ботов имеют строгие лимиты запросов в минуту. |
| **Шифрование S3** | Все данные товаров зашифрованы (SSE-S3). Доступ только по временным pre-signed URL. |

### 18.2. Защита от внутренних угроз

| Мера | Описание |
| --- | --- |
| **Аудит-логи** | Каждое действие сотрудника, изменяющее данные или баланс, записывается в неизменяемый лог. |
| **Минимальные привилегии** | Каждый сотрудник имеет доступ только к необходимым функциям. |
| **Обязательный 2FA** | Все сотрудники с доступом к Admin Panel или финансовым операциям обязаны использовать 2FA. |
| **Холдирование средств** | Средства продавца замораживаются (холд) на 72 часа для защиты покупателя. |
