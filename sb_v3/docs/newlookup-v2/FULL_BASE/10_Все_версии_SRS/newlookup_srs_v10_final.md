## 1. Введение

### 1.1. Назначение документа

Настоящее Техническое Задание (ТЗ) описывает все функциональные и нефункциональные требования к системе **Newlookup v9.0**. Документ предназначен для команды разработки (для реализации в Cursor), менеджеров проекта и тестировщиков. Он является единым источником правды по всем аспектам системы.

### 1.2. Область действия

Система Newlookup представляет собой многокомпонентную платформу для продажи цифровых товаров и услуг через Telegram-ботов. Она включает в себя ботов для клиентов, продавцов, партнёров, службы поддержки и владельца системы, а также веб-панель для администрирования.

### 1.3. Руководящие принципы

1. **Надёжность:** Система должна работать стабильно 24/7.

1. **Безопасность:** Все данные (пользователей, транзакций, товаров) должны быть надёжно защищены.

1. **Масштабируемость:** Архитектура должна позволять легко добавлять новые функции и выдерживать рост нагрузки.

1. **Удобство:** Интерфейсы ботов и веб-панели должны быть интуитивно понятными.

1. **Автоматизация:** Максимальное количество процессов должно быть автоматизировано.

## 2. Архитектура системы

### 2.1. Компоненты системы

Система состоит из 8 независимых, но взаимосвязанных компонентов:

| Компонент | Описание |
| --- | --- |
| **Shared** | Общая кодовая база: модели БД, сервисы, утилиты. |
| **Mirror Bot** | Основной бот для клиентов. Через него происходят все покупки. |
| **Seller Bot** | Бот для продавцов для управления товарами и финансами. |
| **Main Bot** | Бот для владельца системы для управления зеркалами и просмотра статистики. |
| **Marketer Bot** | Бот для реферальных партнёров для создания ботов-прокси и отслеживания доходов. |
| **Support Bot** | Бот для службы поддержки с ролевой моделью доступа. |
| **Worker Bot** | Бот для исполнителей заказов (Per Order). |
| **Admin Panel** | Веб-интерфейс для полного управления системой. |

### 2.2. Технологический стек

| Компонент | Технология |
| --- | --- |
| **Язык** | Python 3.11+ |
| **Фреймворк ботов** | Aiogram 3.x |
| **Веб-фреймворк** | FastAPI |
| **База данных** | PostgreSQL (асинхронный доступ через SQLAlchemy 2.0) |
| **Кэш / Очереди** | Redis |
| **Планировщик задач** | APScheduler |
| **Файловое хранилище** | S3-совместимое (MinIO, Yandex Object Storage и т.д.) |
| **Приём платежей** | BTCPay Server, Helecat |

### 3.2. Ключевые изменения в v9

1. **Единая таблица ****`withdrawal_requests`****:** Все заявки на вывод (от продавцов, воркеров, маркетологов, владельцев ботов) теперь хранятся в одной таблице для централизованной обработки ролью `finance`.

1. **Мультиязычные рассылки:** Таблица `broadcasts` теперь содержит отдельные поля для каждого языка (`message_text_en`, `message_text_ru` и т.д.).

1. **Динамические категории:** Таблица `mirror_menu_categories` позволяет управлять кнопками в главном меню Mirror Bot через Admin Panel.

1. **Детальные модели товаров:** Для каждого типа товара от продавца (Selfreg BA, Selfreg CC, Logs BA, Enroll, NFC, OTP, Checks) создана отдельная таблица со всеми необходимыми полями.

## 4. Mirror Bot: Клиентский Бот

### 4.1. Обзор

Mirror Bot — это основной интерфейс для взаимодействия покупателей с платформой. Он предоставляет доступ ко всему каталогу товаров и услуг, управлению профилем, балансом и поддержкой.

### 4.2. Флоу: Первый запуск и регистрация

1. **REQ-MB-001:** При первом запуске бота (`/start`) пользователь должен принять правила сервиса. Кнопка "✅ Принять правила" становится доступной только после того, как пользователь нажал на кнопку "Читать правила".

1. **REQ-MB-002:** После принятия правил пользователь видит главное меню.

1. **REQ-MB-003:** В базу данных создаётся новая запись в таблице `users` с привязкой к `mirror_bot_id` и, если применимо, `marketer_id` (если пользователь пришёл по ссылке партнёра).

### 4.3. Главное меню

**REQ-MB-004:** Главное меню является динамическим и управляется из Admin Panel (см. раздел 9.3). Администратор может добавлять, удалять, переименовывать и менять порядок категорий.

Пример структуры меню:

- 🏦 Banks

- 💳 CC

- 🔍 Lookup

- 📦 Brute Bank

- 💼 Accounts (Proxy, AI)

- 📱 eSIM

- ... (другие категории)

### 4.4. Профиль и Баланс

**REQ-MB-005:** Раздел "👤 Профиль" должен отображать следующую информацию:

- **User ID:** Telegram ID пользователя.

- **Баланс:** Текущий баланс в USD.

- **Всего пополнено:** Общая сумма пополнений.

- **Всего потрачено:** Общая сумма заказов.

- **Кнопки:** "Пополнить баланс", "Мои заказы", "Поддержка", "Реферальная программа".

**REQ-MB-006:** Пополнение баланса осуществляется через несколько платёжных систем:

- **BTCPay:** Прямая интеграция.

- **Helecat:** Внешний сервис.

- **Crypto Bot (Telegram):** Через чеки.

**REQ-MB-007:** Пользователь может отправить деньги другому пользователю внутри системы по его Telegram ID (`Send money`).

### 4.5. Каталог товаров

#### 4.5.1. Banks (Per Order)

**REQ-MB-008:** Категория "Banks" содержит услуги, выполняемые воркерами под заказ.

**REQ-MB-009:** Услуги делятся на три типа:

1. **Per Order (Стандартный):** Заказ уходит воркерам, назначенным на эту услугу.

1. **Per Order (Same Name/Address):** Пользователь дополнительно вводит имя и адрес для выполнения заказа.

1. **In Stocks (от Продавцов):** Товары от продавцов, которые доступны мгновенно (см. раздел 5).

**REQ-MB-010:** Администратор может добавлять новые подкатегории и услуги в Admin Panel и привязывать к ним воркеров (см. раздел 9.4).

#### 4.5.2. Brute Bank

**REQ-MB-011:** Покупатель видит список категорий банков (`BruteBankGroup`), отформатированный как `BankName [Интеграции] [Кол-во]`. Пример: `Chase [AN:RN+INST YODLEE] [242]`.

**REQ-MB-012:** После выбора категории покупатель видит цену за одну строку и может купить определённое количество.

**REQ-MB-013:** После покупки пользователь получает в чат купленные строки из таблицы `brute_bank_items`.

#### 4.5.3. Logs BA

**REQ-MB-014:** Покупатель видит список доступных лотов. Каждый лот представляет собой карточку товара, сгенерированную из данных, введённых продавцом в конфигураторе.

**REQ-MB-015:** При покупке пользователь получает доступ к файлу, хранящемуся в S3. Доступ предоставляется после нажатия на кнопку "Я понимаю риски и принимаю условия", которая отображает гарантийную политику.

#### 4.5.4. Selfreg (BA и CC)

**REQ-MB-016:** Аналогично Logs BA, покупатель видит список лотов с детальными параметрами, введёнными продавцом. При покупке получает файл из S3.

#### 4.5.5. Accounts (Proxy, AI)

**REQ-MB-017:** Раздел содержит две подкатегории: `Proxy` и `AI`. Товары в этих категориях управляются из Admin Panel и могут быть добавлены вручную или через API.

#### 4.5.6. eSIM

**REQ-MB-018:** Интеграция с внешним API для продажи eSIM. Покупатель выбирает страну и тарифный план. После оплаты система через API запрашивает QR-код и отправляет его пользователю.

### 4.6. Мои заказы

**REQ-MB-019:** В этом разделе пользователь видит историю своих покупок, 

 по типу (товары от продавцов, услуги от воркеров).

**REQ-MB-020:** Для заказов от продавцов (Seller Bot) должна быть кнопка **"Написать продавцу"**. Этот чат доступен до тех пор, пока заказ не будет подтверждён покупателем, и остаётся доступным для чтения после.

**REQ-MB-021:** Покупатель может открыть спор по заказу, если товар не соответствует описанию. Спор уходит в Support Bot на рассмотрение модераторам.

### 4.7. Поддержка

**REQ-MB-022:** Пользователь может создать тикет в поддержку, выбрав категорию. Вся переписка происходит внутри Telegram. Пользователь получает уведомления о новых ответах от поддержки.

## 5. Seller Bot: Бот для Продавцов

### 5.1. Обзор

Seller Bot предназначен для продавцов, которые хотят продавать свои цифровые товары через платформу Newlookup. Бот предоставляет инструменты для регистрации, управления товарами, отслеживания продаж и вывода средств.

### 5.2. Флоу: Регистрация и Залоговый Депозит

1. **REQ-SB-001:** При первом запуске потенциальный продавец должен подать заявку на регистрацию, которая уходит на рассмотрение администратору в Admin Panel.

1. **REQ-SB-002:** После одобрения заявки продавец должен внести залоговый депозит. Сумма депозита зависит от категорий товаров, которые он планирует продавать.

| Пакет | Сумма депозита | Доступные категории |
| --- | --- | --- |
| CC | $300 | CC (with zip, with fullz, non-vbv) |
| Enroll | $200 | Enroll (Debit, Credit), NFC, OTP |
| Selfreg | $150 | Selfreg BA, Selfreg CC |
| Brute/Logs | $300 | Brute Bank, Logs BA |
| Checks | $150 | Checks |
| **ALL** | **$600** | Все категории |

1. **REQ-SB-003:** После успешного внесения депозита продавец получает доступ к полному функционалу бота.

### 5.3. Управление товарами

#### 5.3.1. Конфигураторы товаров

**REQ-SB-004:** Для каждого типа товара (Logs BA, Selfreg BA/CC, Enroll, NFC, OTP, Checks) должен быть реализован пошаговый конфигуратор (FSM) для загрузки.

**Пример флоу для Logs BA:**

1. Продавец выбирает "Загрузить товар" -> "Logs BA".

1. **Шаг 1: Заполнение параметров.** Бот предлагает заполнить форму с полями:
  - Список банков (название, тип счёта, баланс)
  - Тип почты (gmail, aol, outlook и т.д.)
  - Флаги (есть CVV, есть инвестиции, Zelle, Wire и т.д.)
  - Цена лота

1. **Шаг 2: Загрузка файла.** Продавец загружает `.zip` или `.txt` файл с логами.

1. **Шаг 3: Предпросмотр.** Бот генерирует карточку товара и показывает её продавцу для подтверждения.

1. **Шаг 4: Отправка на модерацию.** Товар уходит на проверку в Admin Panel.

#### 5.3.2. Массовая загрузка (Brute Bank, CC)

**REQ-SB-005:** Для товаров типа Brute Bank и CC должна быть реализована массовая загрузка.

1. Продавец выбирает категорию (например, `Chase [AN:RN]`).

1. Бот просит загрузить `.txt` файл, где каждая строка — это один товар в определённом формате (например, `login:password:proxy`).

1. Система парсит файл и добавляет каждую строку как отдельный `brute_bank_item` в базу данных, привязывая к соответствующей `BruteBankGroup`.

### 5.4. Финансы и Вывод средств

**REQ-SB-006:** Продавец видит свой баланс, историю продаж и может запросить вывод средств.

**REQ-SB-007:** Заявка на вывод создаётся в единой таблице `withdrawal_requests` и уходит на подтверждение роли `finance` в Support Bot.

### 5.5. Уведомления

**REQ-SB-008:** Продавец должен иметь возможность настраивать, какие уведомления он хочет получать. Настройки доступны в Seller Mini App.

| Тип уведомления | Описание |
| --- | --- |
| **Новый заказ** | Уведомление о покупке его товара. |
| **Спор по заказу** | Уведомление об открытии спора покупателем. |
| **Сообщение от покупателя** | Новое сообщение в чате заказа. |
| **Статус вывода** | Уведомление об одобрении или отклонении заявки на вывод. |
| **Действия поддержки** | Уведомления о действиях модераторов с его товарами. |

### 5.6. Seller Mini App

**REQ-SB-009:** Для продавцов должно быть разработано веб-приложение (Mini App), открывающееся внутри Telegram. Оно должно предоставлять расширенные возможности:

- Дашборд с аналитикой продаж.

- Удобный интерфейс для управления большим количеством товаров.

- Настройки уведомлений.

- Просмотр истории всех операций.

## 6. Main Bot: Бот Владельца

### 6.1. Обзор

Main Bot — это административный инструмент для владельца всей системы. Его основной функционал остаётся **без изменений** по сравнению с предыдущими версиями.

### 6.2. Функционал

1. **REQ-MAIN-001:** Владелец может создавать "зеркала" — новые экземпляры Mirror Bot. Для этого он вводит токен нового бота, и система регистрирует его в таблице `mirror_bots`.

1. **REQ-MAIN-002:** Владелец может просматривать общую статистику по всем своим ботам: количество пользователей, доходы, количество заказов.

1. **REQ-MAIN-003:** Владелец может отправлять уведомления пользователям своих ботов.

1. **REQ-MAIN-004:** Вывод средств владельцем бота осуществляется через общую систему `withdrawal_requests` и подтверждается ролью `finance`.

## 7. Marketer Bot: Бот для Партнёров

### 7.1. Обзор

Marketer Bot предназначен для реферальных партнёров (маркетологов), которые привлекают новых пользователей в систему. Система промокодов упраздняется в пользу ботов-прокси.

### 7.2. Флоу работы

1. **REQ-MARK-001:** Маркетолог регистрируется в Marketer Bot.

1. **REQ-MARK-002:** Маркетолог может создать собственного Telegram-бота (бота-прокси). Он вводит токен этого бота в Marketer Bot.

1. **REQ-MARK-003:** Система сохраняет связь в таблице `marketer_bot_links` (`marketer_id` + `mirror_bot_id`).

1. **REQ-MARK-004:** Когда новый пользователь запускает бота-прокси, он фактически взаимодействует с экземпляром Mirror Bot, но в его запись в `users` прописывается `marketer_id` создателя этого бота-прокси.

1. **REQ-MARK-005:** Маркетолог получает **8.5%** с каждого пополнения баланса привлечённых им пользователей.

### 7.3. Защита от злоупотреблений

**REQ-MARK-006:** В интерфейсе Marketer Bot должно быть чётко указано, что ставка составляет 10%, но реальная выплата — 8.5%. Разница в 1.5% удерживается для покрытия расходов на антифрод-систему.

**REQ-MARK-007:** Должен быть реализован механизм для борьбы со злоупотреблениями (когда маркетолог сам регистрируется по своей ссылке). В интерфейсе должно быть предупреждение:

> "Наша система использует ИИ для анализа поведения и выявления аномалий. Если более 30% ваших рефералов будут идентифицированы как аффилированные с вами аккаунты, ваш аккаунт в Marketer Bot будет заблокирован без возможности вывода средств."

### 7.4. Аналитика для Маркетологов

**REQ-MARK-008:** Маркетолог должен иметь доступ к дашборду (вкладка в основной Admin Panel или отдельный веб-интерфейс) со следующими метриками:

- Количество созданных ботов.

- Количество привлечённых пользователей (общее и по каждому боту).

- Общая сумма пополнений привлечённых пользователей.

- Заработанная сумма.

- Конверсия (из запусков бота в пополнение).

- LTV (Lifetime Value) и ARPU (Average Revenue Per User) по своим пользователям.

## 8. Support Bot: Бот Поддержки

### 8.1. Обзор

Support Bot — это инструмент для команды поддержки, построенный на основе ролевой модели доступа (RBAC). Каждый сотрудник имеет определённые права в зависимости от своей роли.

### 8.2. Роли и права

| Роль | Описание | Права |
| --- | --- | --- |
| `support` | Сотрудник первой линии поддержки. | - Отвечать на тикеты от пользователей.
- Просматривать информацию о заказах. |
| `finance` | Финансовый менеджер. | - Обрабатывать заявки на вывод средств (одобрять/отклонять).
- **Вручную изменять баланс пользователей с обязательным указанием причины.** |
| `moderator` | Модератор контента. | - Управлять товарами продавцов (одобрять, отклонять, редактировать).
- Разрешать споры между покупателями и продавцами.  
- **Вручную изменять баланс пользователей с обязательным указанием причины.** |
| `uploader` | Контент-менеджер. | - Загружать товары в каталог от имени платформы.
- Имеет доступ только к определённым категориям, назначенным в Admin Panel. |
| `admin` | Администратор. | - Полный доступ к функционалу Support Bot.
- Может управлять ролями других сотрудников. |
| `super_admin` | Владелец системы. | - Все права `admin` + доступ к критически важным операциям. |

### 8.3. Флоу: Обработка вывода средств

1. **REQ-SUP-001:** Когда продавец, воркер, маркетолог или владелец бота запрашивает вывод средств, в Support Bot роли `finance` приходит уведомление.

1. **REQ-SUP-002:** Уведомление содержит всю информацию: кто запрашивает, сумма, метод вывода, текущий баланс.

1. **REQ-SUP-003:** `finance` нажимает "Одобрить" или "Отклонить".

1. **REQ-SUP-004:** В случае одобрения система автоматически отправляет средства. В случае отклонения `finance` должен указать причину.

1. **REQ-SUP-005:** Пользователь, запросивший вывод, получает уведомление о статусе своей заявки.

### 8.4. Флоу: Разрешение споров

1. **REQ-SUP-006:** Когда покупатель открывает спор по заказу, в Support Bot роли `moderator` приходит уведомление.

1. **REQ-SUP-007:** Модератор видит всю историю заказа, переписку между покупателем и продавцом.

1. **REQ-SUP-008:** Модератор может принять решение: вернуть деньги покупателю, оставить деньги продавцу или разделить сумму.

### 8.5. Логирование действий

**REQ-SUP-009:** Все действия сотрудников в Support Bot (особенно изменение баланса, одобрение вывода, решение по спору) должны логироваться в таблице `audit_logs` с указанием, кто, что и когда сделал.

## 9. Admin Panel: Веб-панель Управления

### 9.1. Обзор и Дизайн

Admin Panel — это центральный веб-интерфейс для управления всей системой. Доступ к ней осуществляется по логину и паролю.

**REQ-AP-001:** Дизайн должен быть профессиональным, в тёмной теме, с плотным расположением элементов и без микролагов. Рекомендуемый стек: React + TailwindCSS + shadcn/ui.

### 9.2. Управление доступом (RBAC)

**REQ-AP-002:** Доступ к разделам Admin Panel должен быть основан на ролях, аналогичных Support Bot (`admin`, `super_admin`, `moderator`, `finance`, `uploader`).

### 9.3. Управление каталогом Mirror Bot

**REQ-AP-003:** Раздел "Категории" позволяет управлять главным меню Mirror Bot.

- **Создание/Редактирование:** Название (на 4 языках), иконка, порядок отображения.

- **Включение/Выключение:** Временно скрыть категорию из меню.

**REQ-AP-004:** Для категорий, где работают воркеры (Per Order), должен быть интерфейс для добавления новых подкатегорий (услуг) и привязки к ним конкретных воркеров из таблицы `workers`.

### 9.4. Управление ценами

**REQ-AP-005:** Должен быть единый раздел для управления всеми ценами в системе (таблица `service_prices`). Администратор должен иметь возможность изменять цену на любую услугу или товар.

### 9.5. Управление Купонами

**REQ-AP-006:** Администратор может создавать и управлять скидочными купонами.

| Параметр | Описание |
| --- | --- |
| **Код купона** | Уникальный код (например, `SALE2026`). |
| **Тип скидки** | Фиксированная сумма или процент. |
| **Размер скидки** | Числовое значение. |
| **Время действия** | Дата начала и окончания действия купона. |
| **Лимит активаций** | Максимальное количество использований. |
| **Привязка к услуге** | Можно применить ко всему, к категории или к конкретному товару. |
| **Минимальная сумма заказа** | Купон сработает только если сумма заказа выше указанной. |
| **Одноразовый для пользователя** | Можно ли использовать купон только один раз. |

### 9.6. Рассылки

**REQ-AP-007:** Интерфейс для создания рассылок пользователям Mirror Bot.

- **Мультиязычность:** Отдельные поля для текста на 4 языках (EN, RU, ES, ZH). Если поле для языка пользователя пустое, используется EN.

- **Отложенная публикация:** Возможность запланировать рассылку на определённое время (исключительно по МСК).

### 9.7. Управление Продавцами и Товарами

**REQ-AP-008:** Раздел для модерации. Администратор/модератор видит заявки на регистрацию от новых продавцов и новые товары, ожидающие проверки. Он может одобрить или отклонить их с указанием причины.

### 9.8. Отчёт о прибыльности

**REQ-AP-009:** Дашборд, который показывает финансовые метрики системы: общий доход, расходы (выплаты воркерам, продавцам, маркетологам), чистая прибыль. Фильтры по дате, боту, категории.

#### C.7.3. Антифрод система

**REQ-MKT-001:** Система автоматически выявляет злоупотребления реферальной программой:

1. **Порог активности:** если более 30% пользователей одного маркетолога делают пополнение в первые 24 часа после регистрации — система помечает аккаунт для проверки.

1. **Анализ паттернов:** ИИ-модуль анализирует поведение пользователей (время регистрации, суммы пополнений, IP-адреса, Telegram ID) для выявления мультиаккаунтов.

1. **Автоматический бан:** при обнаружении злоупотребления маркетолог получает статус `suspended` в Marketer Bot. Выплаты замораживаются.

1. **Уведомление:** `super_admin` получает уведомление в Support Bot с деталями нарушения.
