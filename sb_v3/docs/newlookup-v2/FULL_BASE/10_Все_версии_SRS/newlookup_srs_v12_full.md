## 1. Введение и Цели

Newlookup — это многоботовая торговая платформа в Telegram, предназначенная для продажи цифровых товаров и услуг. Система состоит из нескольких специализированных ботов и веб-панели администрирования.

**Ключевые принципы:**
- Все финансовые операции логируются и проходят через единую систему `withdrawal_requests`.
- Все товары от продавцов проходят обязательную модерацию перед публикацией.
- Система поддерживает 4 языка: EN, RU, ES, ZH.
- Все действия сотрудников логируются в `audit_logs`.

## 4. Mirror Bot — Клиентский Бот

### 4.1. Первый запуск и регистрация

**REQ-MB-001:** При первом запуске (`/start`) пользователь обязан принять правила сервиса. Кнопка "✅ Принять правила" становится активной только после нажатия на "Читать правила".

**REQ-MB-002:** После принятия правил создаётся запись в `users` с привязкой к `mirror_bot_id` и, при наличии, к `marketer_id` (если пользователь пришёл через бота-прокси маркетолога).

**REQ-MB-003:** Если пользователь пришёл по реферальной ссылке другого пользователя (`?start=ref_XXXXX`), в его запись прописывается `referrer_id`. Реферер получает 4% с первого пополнения реферала.

### 4.2. Главное меню

**REQ-MB-004:** Главное меню является **полностью динамическим** и управляется из Admin Panel через таблицу `mirror_menu_categories`. Администратор может добавлять, удалять, переименовывать и менять порядок категорий.

Статус наличия товаров отображается в кнопках:
- `🏦 Banks [142]` — количество доступных товаров.
- `📱 eSIM [PREORDER]` — товар доступен для предзаказа.
- `🔍 Lookup` — системный товар без счётчика.

**Текущая структура меню (из кода):**

| Кнопка | Тип | Описание |
| :--- | :--- | :--- |
| 🏦 Banks | Per Order | Услуги по банкам, выполняются воркерами. |
| 💳 CC | In Stocks | Карты от продавцов (with_fullz, zip_only, non_vbv). |
| 🔍 Lookup | Per Order | Системная услуга поиска. |
| 📦 Brute Bank | In Stocks | Данные банковских аккаунтов (AN:RN+INST). |
| 📋 Logs BA | In Stocks | Логи банковских аккаунтов от продавцов. |
| 🏧 Selfreg BA | In Stocks | Саморегистрированные банковские аккаунты. |
| 🏧 Selfreg CC | In Stocks | Саморегистрированные кредитные карты. |
| 🏦 Enroll | In Stocks | Enroll-аккаунты от продавцов. |

### 4.3. Профиль и Баланс

**REQ-MB-005:** Раздел "👤 Профиль" отображает:
- User ID (Telegram ID).
- Текущий баланс в USD.
- Всего пополнено / Всего потрачено.
- Реферальная ссылка и количество рефералов.
- Кнопки: "💳 Пополнить", "📦 Мои заказы", "🎟 Применить купон", "💬 Поддержка", "👥 Рефералы".

**REQ-MB-006:** Пополнение баланса через:
- **BTCPay Server** — прямая интеграция.
- **Helecat** — внешний сервис.
- **Crypto Bot (Telegram)** — через чеки.

**REQ-MB-007:** Пользователь может перевести средства другому пользователю по Telegram ID ("Send money").

**REQ-MB-008 (Купоны):** Пользователь может применить купон:
1. Нажимает "🎟 Применить купон".
2. Вводит код купона.
3. Система проверяет: активность купона, срок действия, лимит использований, минимальную сумму заказа, одноразовость для пользователя.
4. При успехе — скидка применяется к следующему заказу или пополнению (в зависимости от `scope` купона).
5. Защита от повторного применения: запись в `coupon_redemptions` создаётся сразу при применении.

### 4.4. Каталог товаров — Per Order (системные услуги)

**REQ-MB-009:** Для категорий Per Order (Banks, Lookup, Credit Reports, Documents, Education) флоу покупки:
1. Пользователь выбирает услугу и подкатегорию.
2. Видит описание и цену.
3. Подтверждает заказ — деньги списываются с баланса.
4. Создаётся запись в `orders`, уведомление уходит воркеру в Worker Bot.
5. Воркер выполняет заказ и отправляет результат.
6. Пользователь получает результат и может поставить оценку (👍 / 👎).

### 4.5. Каталог товаров — In Stocks (товары продавцов)

**REQ-MB-010:** Для категорий In Stocks флоу покупки:
1. Пользователь выбирает категорию → видит список товаров с пагинацией.
2. Нажимает на товар → видит карточку с параметрами.
3. Нажимает "✅ Купить — $X.XX" → видит предупреждение о политике гарантий.
4. Подтверждает → деньги списываются, товар помечается `is_sold = True`.
5. Пользователь получает файл из S3 (или данные напрямую).
6. В течение гарантийного периода доступны кнопки "👍 Лайк", "👎 Дизлайк", "💬 Что-то не так?".

**REQ-MB-011:** Кнопка "💬 Что-то не так?" открывает спор:
1. Покупатель описывает проблему.
2. Создаётся тикет в `support_tickets` со статусом `dispute`.
3. Уведомление уходит продавцу в Seller Bot и модератору в Support Bot.
4. Покупатель и продавец могут общаться через чат в тикете.
5. Модератор принимает решение: возврат / оставить продавцу / разделить.

### 4.6. Рейтинг товаров и продавцов

**REQ-MB-012:** После покупки (в течение гарантийного периода) пользователь может поставить:
- 👍 Лайк — увеличивает `rating_likes` у продавца.
- 👎 Дизлайк — увеличивает `rating_dislikes` у продавца, создаёт автоматический тикет для модератора.

**REQ-MB-013:** Рейтинг продавца отображается в карточке товара.

### 4.7. Поддержка

**REQ-MB-014:** Кнопка "💬 Поддержка" в профиле открывает тикет в Support Bot:
1. Пользователь выбирает тему обращения.
2. Описывает проблему.
3. Создаётся тикет в `support_tickets` со статусом `open`.
4. Уведомление уходит роли `support` в Support Bot.
5. Переписка ведётся через бота.

### 4.8. Мои заказы

**REQ-MB-015:** Раздел "📦 Мои заказы" показывает историю всех покупок с фильтрацией по статусу (активные, завершённые, споры). Для каждого заказа доступны: повторная выдача файла (если в S3), открытие спора (в течение гарантийного периода), чат с продавцом.

## 5. Seller Bot — Бот Продавца

### 5.1. Доступ и депозит

**REQ-SB-001:** Для получения доступа к загрузке товаров продавец обязан внести **возвратный депозит $600**.

**REQ-SB-002:** Депозит принимается через BTCPay Server. После подтверждения оплаты продавец получает доступ ко **всем** категориям товаров.

**REQ-SB-003:** Депозит возвращается при выходе продавца из системы (при условии отсутствия активных споров и задолженностей).

### 5.2. Главное меню Seller Bot

| Раздел | Описание |
| :--- | :--- |
| 📦 Мои товары | Список всех загруженных товаров с фильтрацией по категории и статусу. |
| ➕ Загрузить товар | FSM-конфигуратор для загрузки нового товара. |
| 📊 Статистика | Краткая статистика: продажи, выручка, рейтинг. |
| 💰 Баланс и вывод | Текущий баланс, история выплат, запрос на вывод. |
| 💬 Тикеты | Активные споры и обращения покупателей. |
| 👥 Помощники | Управление помощниками (UPLOADER / SUPPORT). |
| ⚙️ Настройки | Авто-удаление, уведомления. |

### 5.3. Загрузка товаров (FSM-конфигуратор)

**REQ-SB-004:** Продавец выбирает категорию, затем проходит пошаговый конфигуратор. Все загруженные товары отправляются на модерацию.

Поддерживаемые категории для загрузки:

| Категория | Формат | Описание |
| :--- | :--- | :--- |
| Selfreg BA | Конфигуратор + файл | Пошаговое заполнение параметров + загрузка файла. |
| Selfreg CC | Конфигуратор + файл | Пошаговое заполнение параметров + загрузка файла. |
| Logs BA | Конфигуратор + файл | Выбор категории → конфигуратор → загрузка .zip. |
| Enroll | Конфигуратор + файл | Пошаговое заполнение + загрузка .zip. |
| NFC | Конфигуратор + файл | Пошаговое заполнение + загрузка файла. |
| OTP | Конфигуратор + файл | Пошаговое заполнение + загрузка файла. |
| Checks | Конфигуратор + файл | Пошаговое заполнение + загрузка файла. |
| CC | Выбор типа + .txt | Выбор типа (with_fullz / zip_only / non_vbv) → массовая загрузка. |
| Brute Bank | Выбор группы + .txt | Выбор существующей группы или создание новой → массовая загрузка. |

**REQ-SB-005:** После загрузки система автоматически генерирует карточку товара на основе заполненных параметров и отправляет её на модерацию в Support Bot.

**REQ-SB-006:** Продавец может редактировать параметры загруженного товара (до и после модерации).

### 5.4. Настройки авто-удаления

**REQ-SB-007:** Продавец может настроить правила для залежавшихся товаров:
- **Авто-удаление:** через X дней (продавец задаёт значение) товар автоматически снимается с продажи.
- **Напоминание:** через X дней продавец получает уведомление с предложением снизить цену.
- Настройка применяется глобально ко всем товарам продавца.

### 5.5. Помощники продавца

**REQ-SB-008:** Продавец может добавить помощников с двумя ролями:

| Роль | Права |
| :--- | :--- |
| **UPLOADER** | Может загружать товары только в те категории, которые разрешил продавец. |
| **SUPPORT** | Может отвечать на тикеты покупателей и просматривать заказы. |

### 5.6. Вывод средств

**REQ-SB-009:** Продавец запрашивает вывод средств:
1. Выбирает метод (BTC / XMR).
2. Вводит адрес кошелька и сумму.
3. Создаётся запись в `withdrawal_requests` со статусом `pending`.
4. Уведомление уходит роли `finance` в Support Bot.
5. После одобрения — средства отправляются, баланс обновляется.

### 5.7. Чат с покупателем

**REQ-SB-010:** При открытии спора или обращении покупателя продавец получает уведомление в Seller Bot. Переписка ведётся через бота, все сообщения хранятся в `seller_conversations`.

## 6. Seller Mini App — Веб-приложение Продавца

**REQ-SMA-001:** Seller Mini App — это Telegram Mini App (WebApp), доступное через кнопку в Seller Bot. Предоставляет расширенный интерфейс для управления бизнесом продавца.

## 7. Marketer Bot — Бот Партнёра

### 7.1. Концепция: Боты-прокси

**REQ-MARK-001:** Маркетолог работает через систему **ботов-прокси**. Он регистрирует свой Telegram-бот в системе, и все пользователи, пришедшие через этого бота, автоматически закрепляются за ним.

**Механизм:**
1. Маркетолог регистрируется в Marketer Bot.
2. Вводит токен своего Telegram-бота.
3. Система сохраняет связь в `marketer_bot_links` (`marketer_id` + `mirror_bot_id`).
4. Когда новый пользователь запускает бота-прокси, он взаимодействует с экземпляром Mirror Bot, но в его запись в `users` прописывается `marketer_id`.
5. Маркетолог получает **8.5%** с каждого пополнения баланса привлечённых пользователей.

**REQ-MARK-002:** Маркетолог может создать до **5 ботов-прокси**.

### 7.2. Дашборд маркетолога

**REQ-MARK-003:** Главный экран Marketer Bot показывает:
- Общее количество привлечённых пользователей.
- Количество пользователей по каждому боту-прокси.
- Общая сумма пополнений привлечённых пользователей.
- Заработанная сумма (начислено / выплачено / доступно).
- Конверсия (запуски → первое пополнение).
- CR (Conversion Rate), ARPU, LTV.

### 7.3. Управление ботами-прокси

**REQ-MARK-004:** В разделе "Мои боты":
- Список всех зарегистрированных ботов с метриками по каждому.
- Добавить новый бот (ввод токена).
- Удалить бот (пользователи остаются привязанными к маркетологу).
- Статистика по боту: пользователи, пополнения, заработок.

### 7.4. Вывод средств

**REQ-MARK-005:** Маркетолог запрашивает вывод прямо из Marketer Bot:
1. Выбирает метод (BTC / XMR).
2. Вводит адрес и сумму.
3. Запись в `withdrawal_requests`, уведомление роли `finance`.

### 7.5. Антифрод-защита

**REQ-MARK-006:** В интерфейсе Marketer Bot указывается ставка **10%**, но реальная выплата — **8.5%**. Разница 1.5% удерживается на антифрод.

**REQ-MARK-007:** Предупреждение в боте:
> "Наша система использует ИИ для анализа поведения и выявления аномалий. Если более 30% ваших рефералов будут идентифицированы как аффилированные с вами аккаунты, ваш аккаунт будет заблокирован без возможности вывода средств."

**REQ-MARK-008:** Автоматическая проверка `check_fraud(marketer_id)` перед каждой заявкой на вывод:
- Если один реферал даёт 90%+ бонусов → заявка создаётся со статусом `blocked`, уведомление уходит роли `finance`.
- Логируется причина блокировки.

**REQ-MARK-009:** Уведомление маркетологу при достижении каждых 50 новых регистраций.

## 8. Support Bot — Бот Поддержки

### 8.1. Роли и права

**REQ-SUP-001:** Support Bot реализует детализированную ролевую модель (RBAC):

| Роль | Описание | Права |
| :--- | :--- | :--- |
| `support` | Первая линия поддержки. | Отвечать на тикеты, просматривать заказы. |
| `moderator` | Модератор контента. | Модерировать товары продавцов, разрешать споры, изменять баланс пользователей (с указанием причины). |
| `finance` | Финансовый менеджер. | Обрабатывать заявки на вывод (одобрять/отклонять), изменять баланс пользователей (с указанием причины). |
| `uploader` | Контент-менеджер. | Загружать товары в каталог от имени платформы (только назначенные категории). |
| `admin` | Администратор. | Полный доступ к Support Bot, управление ролями сотрудников. |
| `super_admin` | Владелец системы. | Все права `admin` + критически важные операции. |

### 8.2. Флоу: Обработка вывода средств

1. **REQ-SUP-002:** Запрос на вывод от продавца / воркера / маркетолога / владельца бота → уведомление роли `finance`.
2. **REQ-SUP-003:** Уведомление содержит: кто запрашивает, сумма, метод, текущий баланс, история предыдущих выводов.
3. **REQ-SUP-004:** `finance` нажимает "Одобрить" или "Отклонить" (с обязательным указанием причины при отклонении).
4. **REQ-SUP-005:** При одобрении — средства отправляются автоматически. Пользователь получает уведомление о статусе.

### 8.3. Флоу: Разрешение споров

1. **REQ-SUP-006:** Покупатель открывает спор → уведомление роли `moderator`.
2. **REQ-SUP-007:** Модератор видит: историю заказа, переписку покупателя и продавца, данные товара.
3. **REQ-SUP-008:** Модератор принимает решение: вернуть покупателю / оставить продавцу / разделить сумму.
4. **REQ-SUP-009:** Решение применяется автоматически, обе стороны получают уведомление.

### 8.4. Флоу: Модерация товаров

1. **REQ-SUP-010:** При загрузке нового товара продавцом → уведомление роли `moderator`.
2. **REQ-SUP-011:** Модератор видит карточку товара со всеми параметрами.
3. **REQ-SUP-012:** Одобрить (товар становится активным) / Отклонить (с указанием причины) / Редактировать (изменить цену или параметры).
4. **REQ-SUP-013:** Продавец получает уведомление о результате модерации.

### 8.5. Логирование действий

**REQ-SUP-014:** Все действия сотрудников логируются в `audit_logs`:
- Изменение баланса пользователя.
- Одобрение/отклонение вывода средств.
- Решение по спору.
- Одобрение/отклонение товара.
- Бан пользователя или продавца.

## 12. Финансовая Модель

### 12.1. Расчёт прибыли

```
Прибыль = Цена_покупателя - Выплата_продавцу - Выплата_воркеру - Выплата_маркетологу
```

- **Цена_покупателя:** финальная цена с наценкой системы.
- **Выплата_продавцу:** цена продавца (без наценки системы).
- **Выплата_воркеру:** фикс или % от цены заказа (Per Order).
- **Выплата_маркетологу:** 8.5% от пополнения привлечённого пользователя.

### 12.2. Реферальная система пользователей

- Пользователь получает **4%** с первого пополнения реферала.
- Реферальная ссылка: `https://t.me/BotName?start=ref_USERID`.

### 12.3. Система купонов

- Купоны могут давать скидку на покупку товара или на пополнение баланса.
- Скидка применяется до списания средств.
- Все применения купонов логируются в `coupon_redemptions`.

### 13.4. Brute Bank

**REQ-PROD-007:** Структура Brute Bank — два уровня:

**Уровень 1: `BruteBankGroup` (Категория)**

| Поле | Описание |
| :--- | :--- |
| `bank_name` | Название банка. |
| `attributes` | Строка атрибутов, генерируется автоматически конфигуратором. Пример: `AN:RN+INST YODLEE+NAME+ADDRESS`. |
| `price_per_item` | Цена за одну строку в USD. |
| `items_count` | Количество доступных строк (вычисляется автоматически). |

**Уровень 2: `BruteBankItem` (Строка)**

| Поле | Описание |
| :--- | :--- |
| `group_id` | Привязка к группе. |
| `data` | Зашифрованные данные строки. |
| `is_sold` | Флаг продажи. |

**REQ-PROD-008:** Покупатель видит список групп: `Chase [AN:RN+INST YODLEE] [242]`.

**REQ-PROD-009:** Загрузка продавцом:
1. Выбирает существующую группу или создаёт новую (через Admin Panel).
2. Загружает `.txt` файл — каждая строка один аккаунт.
3. Система парсит и добавляет каждую строку как отдельный `BruteBankItem`.

**Поддерживаемые атрибуты:**
- `AN` — Account Number
- `RN` — Routing Number
- `NAME` — Имя владельца
- `ADDRESS` — Адрес
- `CITY` — Город
- `ZIP` — ZIP-код
- `ONLINE ACCESS` — Онлайн-доступ
- `INST YODLEE` — Интеграция Yodlee
- `INST FINICITY` — Интеграция Finicity
- `INST PLAID` — Интеграция Plaid
- `INST MX` — Интеграция MX
- `INST AKOYA` — Интеграция Akoya
- (и другие — список расширяемый через Admin Panel)

### 13.5. CC (Кредитные Карты от Продавцов)

**REQ-PROD-010:** Продавец сначала выбирает тип карты, затем загружает `.txt` файл. Система проверяет каждую строку по BIN (первые 6–8 цифр) и количеству полей.

| Подтип | Формат строки | Описание |
| :--- | :--- | :--- |
| `with_fullz` | `card;exp_month;exp_year;cvv;zip;name;address;ssn;dob;phone` | Карта с полными данными. |
| `zip_only` | `card;exp_month;exp_year;cvv;zip` | Карта только с ZIP. |
| `non_vbv` | `card;exp_month;exp_year;cvv` | Карта без VBV-проверки. |

**REQ-PROD-011:** Проверка при загрузке:
1. Продавец выбирает тип (`with_fullz` / `zip_only` / `non_vbv`).
2. Загружает `.txt` файл.
3. Система проверяет каждую строку: соответствие формату выбранного типа по количеству полей.
4. BIN-проверка: первые 6–8 цифр карты сверяются с базой BIN для определения банка и типа карты.
5. Строки с ошибками отображаются в отчёте о загрузке.

### 13.6. eSIM (Ручное Управление)

**REQ-PROD-012:** Администратор в Admin Panel управляет тарифами eSIM вручную. Никакой внешней API-интеграции нет.

После покупки покупателем:
1. Администратор получает уведомление в Admin Panel.
2. Вручную загружает QR-код или файл активации для клиента.
3. Покупатель получает файл через Mirror Bot.

### 13.7. Accounts (Proxy, AI) — Предзаказ

**REQ-PROD-013:** Продажа Proxy и AI аккаунтов работает по модели **предзаказа**:
1. Покупатель выбирает тип аккаунта и оставляет заявку.
2. Заявка отображается в Admin Panel.
3. Администратор обрабатывает вручную: находит/создаёт аккаунт, загружает данные.
4. Покупатель получает данные через Mirror Bot.

Товары не хранятся в наличии — приобретаются/создаются под конкретный заказ.
