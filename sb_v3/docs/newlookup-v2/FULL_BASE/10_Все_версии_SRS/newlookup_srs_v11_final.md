## 1. Введение

Настоящее Техническое Задание (ТЗ) описывает все функциональные и нефункциональные требования к системе **Newlookup v11.0**. Документ предназначен для команды разработки, менеджеров проекта и тестировщиков. Он является единым источником правды по всем аспектам системы.

---

## 2. Архитектура и Роли

Система представляет собой мультисервисную Python-систему, где основной пользовательский интерфейс находится в Telegram-ботах, а внутреннее управление вынесено в веб-панель (Admin Panel). Все сервисы (Mirror, Seller, Main, Marketer, Support, Worker боты) работают вокруг общей базы данных и бизнес-логики.

---

## 3. Mirror Bot: Клиентский Бот

### 3.1. Главное меню

**REQ-MB-001:** Главное меню Mirror Bot имеет следующую статическую структуру, основанную на текущей кодовой базе:

*   **Search / Lookup:** Поиск информации (SSN, DOB, Credit Score и т.д.).
*   **Credit Reports:** Кредитные отчёты.
*   **Documents:** Документы.
*   **Pros & Fullz:** Профессиональные данные и Fullz.
*   **Banks:** Банковские продукты (включая товары от продавцов).
*   **Subscriptions / Accounts:** Аккаунты и подписки (Proxy, AI).
*   **eSIM:** Продажа eSIM.
*   **Add info in CR:** Добавление информации в кредитный отчёт.
*   **Support:** Поддержка.
*   **Referrals:** Реферальная программа.
*   **Call Service:** Услуги прозвона.

### 3.2. Профиль и Баланс

**REQ-MB-002:** В разделе "Профиль" добавлена кнопка **"Применить купон"**. Система должна проверять купон на валидность (существование, срок действия, лимит использований) и защищать от многократного применения одним пользователем.

### 3.3. Каталог товаров

#### 3.3.1. Accounts (Proxy, AI) — Предзаказ

**REQ-MB-003:** Раздел **Subscriptions / Accounts** работает по модели **предзаказа**. Покупатель оставляет заявку, которая уходит в Admin Panel. Администратор обрабатывает её вручную и доставляет товар покупателю. Автоматической выдачи нет.

#### 3.3.2. eSIM — Ручное управление

**REQ-MB-004:** Раздел **eSIM** работает через ручное управление в Admin Panel. Интеграции с внешними API нет. Администратор вручную добавляет тарифы (страна, объём, срок, цена), а после покупки вручную загружает QR-код или файл для покупателя.

### 3.4. Мои заказы и Споры

**REQ-MB-005:** В разделе "Мои заказы" пользователь может **открыть спор** по заказу. Эта функция является аналогом **жалобы**. Спор немедленно создаёт тикет в Support Bot, где его обрабатывают модераторы.

### 3.5. Поддержка

**REQ-MB-006:** При нажатии на кнопку **Support** в главном меню, пользователь перенаправляется в Support Bot, где он может создать тикет, выбрав соответствующую категорию. Вся коммуникация с поддержкой происходит централизованно в Support Bot.

## 4. Seller Bot и Seller Mini App

### 4.1. Обзор и Mini App

**REQ-SB-001:** Seller Bot работает в гибридной модели: базовые функции доступны через команды в боте, а расширенная аналитика, управление товарами и настройки — через **Telegram Mini App**.

### 4.2. Рейтинг продавца

**REQ-SB-002:** После завершения заказа покупателю предлагается оценить продавца, поставив **лайк** или **дизлайк**. Рейтинг продавца (соотношение лайков и дизлайков) виден покупателям в карточке товара и в профиле продавца в Mini App.

### 4.3. Конфигураторы товаров

**REQ-SB-003:** Для каждого типа товара реализован пошаговый конфигуратор. Продавец может редактировать загруженный товар. Также продавец в настройках может установить правила авто-удаления или напоминания о снижении цены для залежавшихся товаров (например, через 30 дней).

---

## 5. Marketer Bot: Бот для Партнёров

**REQ-MARK-001:** Маркетолог работает через **ботов-прокси**. Он регистрирует свой Telegram-бот в системе, и все пользователи, пришедшие через этого бота, закрепляются за ним. Таблица `marketer_bot_links` хранит эту связь. Маркетолог может запрашивать вывод средств прямо из Marketer Bot, заявка уходит на обработку роли `finance`.

---

## 6. Support Bot: Роли и Права

**REQ-SUP-001:** В Support Bot и Admin Panel реализована детализированная ролевая модель:

*   **Support:** Обрабатывает споры и общие вопросы.
*   **Moderator:** Модерирует товары продавцов, одобряет новые категории.
*   **Finance:** Обрабатывает все заявки на вывод средств (от продавцов, воркеров, маркетологов).
*   **Admin/Super Admin:** Полный доступ ко всем функциям.

## 7. Детальные Спецификации Товаров

### 7.1. Selfreg BA

**REQ-PROD-001:** Конфигуратор Selfreg BA:

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `bank` | Строка | Название банка. |
| `account_type` | Строка | Тип счёта (Checking, Savings). Можно ввести свой, уйдёт на модерацию. |
| `state` | Строка | Штат регистрации. |
| `registration_date` | Дата | Дата регистрации аккаунта (вводится продавцом). |
| `phone_access` | Булево | Есть ли доступ к телефону. |
| `phone_renewable` | Булево | Можно ли продлить номер. |
| `phone_change_allowed` | Булево | Можно ли сменить номер, если нет доступа. |
| `email_access` | Булево | Есть ли доступ к email. |
| `email_change_allowed` | Булево | Можно ли сменить email, если нет доступа. |
| `price` | Число | Цена лота в USD. |

### 7.2. Selfreg CC

**REQ-PROD-002:** Конфигуратор Selfreg CC:

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `bank_name` | Выбор | Выбор из предзагруженного списка. Новый банк — через модерацию. |
| `card_name` | Строка | Название карты. |
| `credit_limit` | Число | Кредитный лимит. |
| `has_vcc` | Булево | Есть ли VCC? (да/нет) |
| `vcc_limit` | Число | Лимит VCC (если `has_vcc` = да). |
| `state` | Строка | Штат. |
| `zip` | Строка | ZIP-код. |
| `billing_address` | Строка | Биллинговый адрес. |
| `registration_date` | Дата | Дата регистрации (вводится продавцом). |
| `phone_access` | Булево | Доступ к номеру. |
| `phone_renewable` | Булево | Можно ли продлить номер. |
| `phone_change_allowed` | Булево | Можно ли сменить номер. |
| `email_access` | Булево | Доступ к email. |
| `email_change_allowed` | Булево | Можно ли сменить email. |
| `price` | Число | Цена лота в USD. |

### 7.3. Logs BA

**REQ-PROD-003:** Продавец сначала выбирает категорию лога (например, `USA Bank Log`, `EU Bank Log`), затем заполняет конфигуратор:

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `banks` | JSON | Список банков в логе (название, тип счёта, баланс). |
| `total_balance` | Число | Суммарный баланс (рассчитывается или вводится вручную). |
| `email_type` | Выбор | Тип почты (gmail, aol, etc.). |
| `email_valid` | Булево | Валидность почты. |
| `has_investments` | Булево | Есть ли инвестиционный счёт. |
| `has_credit_line` | Булево | Есть ли кредитная линия. |
| `has_cookies` | Булево | Есть ли cookies. |
| `has_screenshot` | Булево | Есть ли скриншот. |
| `price` | Число | Цена лота в USD. |

### 7.4. Brute Bank

**REQ-PROD-004:** Категория (`category`) для Brute Bank — это строка атрибутов, например `AN:RN+INST YODLEE`. Администратор управляет списком доступных интеграций (`INST`). Поле `address` разделено на `address`, `city`, `zip`.

**REQ-PROD-005:** Массовая загрузка работает через выбор категории. Продавец выбирает `Chase [AN:RN+INST YODLEE]`, затем загружает `.txt` файл, где каждая строка соответствует этому формату. Система не определяет формат автоматически.

### 7.5. CC (Массовая загрузка)

**REQ-PROD-006:** Продавец сначала выбирает тип карты (`with_fullz`, `zip_only`, `non_vbv`), а затем загружает `.txt` файл. Система проверяет каждую строку на соответствие формату выбранного типа по BIN (первые 6-8 цифр номера карты) и количеству полей.

### 7.6. eSIM (Ручное управление)

**REQ-PROD-007:** Администратор в Admin Panel управляет тарифами eSIM:

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `country` | Строка | Страна. |
| `data_volume_gb` | Число | Объём данных в ГБ. |
| `duration_days` | Число | Срок действия в днях. |
| `price` | Число | Цена для покупателя в USD. |
| `is_active` | Булево | Включен/выключен тариф. |

После покупки администратор вручную загружает QR-код для клиента.

### 7.7. Accounts (Proxy, AI) — Предзаказ

**REQ-PROD-008:** Продажа аккаунтов Proxy и AI работает по модели **предзаказа**. Покупатель выбирает тип аккаунта, оставляет заявку. Заявка падает в Admin Panel, где администратор обрабатывает её вручную. Товары не хранятся в наличии, а приобретаются/создаются под конкретный заказ.
