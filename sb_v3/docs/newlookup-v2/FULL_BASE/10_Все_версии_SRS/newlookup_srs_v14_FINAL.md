## 1. Философия и Стратегия {#1}

Newlookup — это не просто маркетплейс, а **экосистема для роста**. Вся архитектура и логика подчинены одной цели: **масштабирование через партнёров**. Система спроектирована так, чтобы каждый участник — продавец, маркетолог, воркер — был мотивирован привлекать новых пользователей и увеличивать оборот.

| Принцип | Описание |
| :--- | :--- |
| **Всё есть API** | Любой элемент системы доступен через внутренний API, что позволяет легко добавлять новые интерфейсы. |
| **Единый источник правды** | База данных PostgreSQL — единственный источник достоверной информации. |
| **Асинхронность** | Вся система построена на асинхронных операциях для высокой производительности. |
| **Zero Trust** | Все действия, влияющие на финансы или данные, проходят несколько уровней проверки и логируются. |
| **Рост через делегирование** | Система поощряет создание команд (продавцы + помощники, маркетологи + боты-прокси). |
| **Многоязычность** | Система поддерживает 4 языка: EN, RU, ES, ZH. |

## 3. Ролевая Модель (RBAC) {#3}

Система имеет 7 ключевых ролей, каждая со своими правами и интерфейсами.

| Роль | Основной интерфейс | Ключевая задача |
| :--- | :--- | :--- |
| **Пользователь** | Mirror Bot | Покупка товаров и услуг. |
| **Продавец** | Seller Bot, Seller Mini App | Продажа товаров, управление командой. |
| **Помощник продавца** | Seller Bot | Помощь продавцу (загрузка товаров, поддержка). |
| **Маркетолог** | Marketer Bot | Привлечение пользователей через ботов-прокси. |
| **Воркер** | Worker Bot | Выполнение заказов Per Order. |
| **Сотрудник поддержки** | Support Bot, Admin Panel | Модерация, споры, финансовые операции. |
| **Владелец** | Main Bot, Admin Panel | Стратегическое управление, аналитика. |

### 3.1. Права сотрудников поддержки

| Роль | Права |
| :--- | :--- |
| `L1 Support` | Отвечать на тикеты, просматривать заказы. Нет доступа к финансам. |
| `L2 Support (Moderator)` | Модерировать товары, решать споры, блокировать пользователей/продавцов. |
| `Finance` | Обрабатывать заявки на вывод, изменять баланс (с указанием причины). |
| `Uploader` | Загружать товары в каталог от имени платформы (только назначенные категории). |
| `Admin` | Полный доступ к Support Bot, управление ролями сотрудников. |
| `Auditor` | Read-only доступ ко всем логам и операциям для контроля. |
| `Super Admin` | Все права Admin + критически важные операции. |

## 5. Mirror Bot — Клиентский Бот {#5}

### 5.1. Регистрация и онбординг

**REQ-MB-001:** При первом запуске бота (`/start`):

1.  Бот определяет язык пользователя по настройкам Telegram.
2.  Отправляет приветственное сообщение (на языке пользователя).
3.  Регистрирует пользователя в таблице `users`, привязывает к текущему `mirror_bot_id`.
4.  Если пользователь пришёл через реферальную ссылку (`/start ref_XXXXX`) — записывает `referrer_id`.
5.  Если пользователь пришёл через бота-прокси маркетолога — записывает `marketer_id`.
6.  Показывает главное меню.

### 5.2. Главное меню

**REQ-MB-002:** Главное меню формируется динамически из таблицы `mirror_menu_categories`. Каждая категория имеет иконку, название на 4 языках и порядок отображения.

**Текущая структура меню (из кода):**

| Кнопка | Тип | Описание |
| :--- | :--- | :--- |
| 🔍 Search | Per Order | Поиск по базам данных. |
| 📊 Credit Reports | Per Order | Кредитные отчёты. |
| 🏦 Banks | In Stocks | Банковские продукты (Selfreg BA, Logs BA, Brute Bank). |
| 💳 Cards | In Stocks | Карты (Selfreg CC, CC). |
| 📱 eSIM | Manual | Виртуальные SIM-карты. |
| 🤖 AI Accounts | Pre-order | AI-аккаунты (предзаказ). |
| 🌐 Proxy | Pre-order | Прокси-аккаунты (предзаказ). |
| 📋 Checks | In Stocks | Чеки. |
| 🔐 OTP | In Stocks | OTP-коды. |
| 📲 NFC | In Stocks | NFC-данные. |
| 📝 Enroll | In Stocks | Enroll-аккаунты. |

### 5.3. Профиль пользователя

**REQ-MB-003:** Раздел "Профиль" содержит:

-   Telegram ID и username.
-   Текущий баланс.
-   Уровень лояльности (Bronze / Silver / Gold / Platinum) с прогрессом до следующего уровня.
-   Реферальная ссылка.
-   Кнопка "Пополнить баланс".
-   Кнопка "Применить купон".
-   Кнопка "История заказов".

### 5.4. Пополнение баланса

**REQ-MB-004:** Флоу пополнения:

1.  Пользователь выбирает метод: BTCPay (BTC), Helecat (карта), Crypto Bot.
2.  Система создаёт инвойс через соответствующий API.
3.  Пользователь оплачивает.
4.  Вебхук подтверждает оплату → баланс пополняется.
5.  Если у пользователя есть `marketer_id` — маркетологу начисляется 8.5% от суммы пополнения.
6.  Если у пользователя есть `referrer_id` — рефереру начисляется 4% от суммы пополнения.

### 5.5. Применение купона

**REQ-MB-005:** Флоу применения купона:

1.  Пользователь вводит код купона.
2.  Система проверяет: существование, срок действия, лимит использований, минимальную сумму заказа, одноразовость (уже использовал этот пользователь или нет).
3.  Если купон валиден — скидка применяется к следующему заказу.
4.  Запись в `coupon_redemptions`.

**Защита от злоупотреблений:**

-   Один купон нельзя применить дважды одним пользователем (если `is_one_per_user = true`).
-   Купон с истёкшим сроком или исчерпанным лимитом отклоняется с понятным сообщением.

### 5.6. Per Order — Заказ услуги

**REQ-MB-006:** Флоу заказа Per Order (например, "Search"):

1.  Пользователь выбирает категорию.
2.  Видит описание услуги и цену.
3.  Нажимает "Заказать" → вводит данные для запроса (имя, адрес, телефон и т.д.).
4.  Подтверждает заказ → баланс списывается.
5.  Если для категории включён **параметр автоматизации** — запрос уходит в Модуль Автоматизации.
6.  Если нет — уведомление уходит назначенному воркеру.
7.  Пользователь видит статус: "⏳ В обработке... Ожидаемое время: ~15 минут".

### 5.7. In Stocks — Покупка товара

**REQ-MB-007:** Флоу покупки товара In Stocks:

1.  Пользователь выбирает категорию.
2.  Видит список доступных товаров с параметрами и ценами.
3.  Выбирает товар → видит детальную карточку.
4.  Нажимает "Купить" → подтверждение.
5.  Баланс списывается, товар помечается как `sold`.
6.  Пользователь получает данные товара в боте.

### 5.8. Споры

**REQ-MB-008:** Кнопка "Открыть спор" доступна в течение **72 часов** после получения товара.

Флоу:

1.  Пользователь нажимает "Открыть спор" → выбирает причину.
2.  Создаётся тикет в `support_tickets` со статусом `dispute`.
3.  Уведомление уходит роли `Moderator` в Support Bot.
4.  Пользователь получает ID тикета и может отслеживать статус.

### 5.9. Рейтинг

**REQ-MB-009:** После завершения заказа (или через 24 часа, если оценка не поставлена) пользователю предлагается оценить товар: 👍 Лайк / 👎 Дизлайк. Оценка сохраняется в `ratings`.

### 5.10. Закрепление выполненных заказов

**REQ-MB-015:** После успешного выполнения заказа (статус `completed`), в чате с пользователем появляется **закреплённое сообщение** с кратким отчётом и кнопками.

**Структура закреплённого сообщения:**

```
✅ Заказ #12345 выполнен!

Тип: Пробив номера
Результат: прикреплён файл ниже

[📄 Полный отчёт] [⚠️ Открыть спор] [⭐ Оценить]
```

-   **"Полный отчёт":** Отправляет `.txt` файл с полным результатом.
-   **"Открыть спор":** Инициирует флоу спора (доступна 72 часа).
-   **"Оценить":** Предлагает поставить лайк/дизлайк.

Закреплённое сообщение остаётся до начала нового заказа. Реализуется через `pin_message` Telegram Bot API.

### 5.11. История заказов

**REQ-MB-010:** Раздел "Мои заказы" показывает список последних 20 заказов с возможностью постраничной навигации. Каждый заказ: тип, дата, статус, кнопка "Повторить".

### 5.12. Поддержка

**REQ-MB-011:** Кнопка "Поддержка" перенаправляет пользователя в Support Bot с автоматическим созданием тикета.

## 8. Marketer Bot — Бот Партнёра {#8}

### 8.1. Концепция: Боты-прокси

**REQ-MARK-001:** Маркетолог работает через систему **ботов-прокси**. Он регистрирует свой Telegram-бот в системе, и все пользователи, пришедшие через этого бота, автоматически закрепляются за ним.

**Механизм работы:**

1.  Маркетолог регистрируется в Marketer Bot.
2.  Нажимает "Создать бота" и вводит токен своего Telegram-бота.
3.  Система сохраняет связь в `marketer_bot_links` (`marketer_id` + `mirror_bot_id`).
4.  Когда новый пользователь запускает бота-прокси, в его запись в `users` прописывается `marketer_id`.
5.  Маркетолог получает **8.5%** с каждого пополнения баланса привлечённых пользователей.

**REQ-MARK-002:** Маркетолог может создать до **5 ботов-прокси**.

**REQ-MARK-003 (Кастомизация):** Маркетолог может изменить приветственное сообщение бота и добавить свои кнопки в главное меню (например, ссылку на свой канал).

### 8.2. Дашборд маркетолога

| Метрика | Описание |
| :--- | :--- |
| Привлечённые пользователи | Общее количество + по каждому боту-прокси. |
| Общая сумма пополнений | Суммарные пополнения привлечённых пользователей. |
| Заработано | Начислено / выплачено / доступно к выводу. |
| Конверсия | Запуски → первое пополнение (CR%). |
| ARPU | Средний доход с привлечённого пользователя. |

### 8.3. Управление ботами-прокси

**REQ-MARK-005:** В разделе "Мои боты": список всех зарегистрированных ботов с метриками по каждому, добавить новый бот (ввод токена), удалить бот (пользователи остаются привязанными к маркетологу).

### 8.4. Вывод средств

**REQ-MARK-006:** Маркетолог запрашивает вывод из Marketer Bot: выбирает метод (BTC / XMR), вводит адрес и сумму → запись в `withdrawal_requests` → уведомление роли `Finance`.

### 8.5. Антифрод-защита

**REQ-MARK-007:** В интерфейсе Marketer Bot указывается ставка **10%**, но реальная выплата — **8.5%**. Разница 1.5% удерживается на антифрод.

**REQ-MARK-008:** Предупреждение в боте:

> "Наша система использует ИИ для анализа поведения и выявления аномалий. Если более 30% ваших рефералов будут идентифицированы как аффилированные с вами аккаунты, ваш аккаунт будет заблокирован без возможности вывода средств."

**REQ-MARK-009:** Автоматическая проверка `check_fraud(marketer_id)` перед каждой заявкой на вывод:

| Условие | Действие |
| :--- | :--- |
| Один реферал даёт 90%+ бонусов | Заявка создаётся со статусом `blocked`, уведомление роли `Finance`. |
| 30%+ рефералов — аффилированные аккаунты | Временная заморозка, уведомление роли `Admin`. |

**REQ-MARK-010:** Уведомление маркетологу при достижении каждых 50 новых регистраций.

## 9. Support Bot — Бот Поддержки {#9}

### 9.1. Роли и права

**REQ-SUP-001:** Support Bot реализует детализированную ролевую модель (RBAC) — см. раздел 3.1.

### 9.2. Флоу: Обработка вывода средств

1.  Запрос на вывод от продавца / воркера / маркетолога / владельца → уведомление роли `Finance`.
2.  Уведомление содержит: кто запрашивает, сумма, метод, текущий баланс, история предыдущих выводов.
3.  `Finance` нажимает "Одобрить" или "Отклонить" (с обязательным указанием причины при отклонении).
4.  При одобрении — средства отправляются автоматически. Пользователь получает уведомление о статусе.

### 9.3. Флоу: Разрешение споров

1.  Покупатель открывает спор → уведомление роли `Moderator`.
2.  Модератор видит: историю заказа, переписку покупателя и продавца, данные товара.
3.  Модератор принимает решение: вернуть покупателю / оставить продавцу / разделить сумму.
4.  Решение применяется автоматически, обе стороны получают уведомление.

### 9.4. Флоу: Модерация товаров

1.  При загрузке нового товара продавцом → уведомление роли `Moderator`.
2.  Модератор видит карточку товара со всеми параметрами.
3.  Одобрить (товар становится активным) / Отклонить (с указанием причины) / Редактировать.
4.  Продавец получает уведомление о результате модерации.

### 9.5. Автоматизация рутины

**REQ-SUP-002:** Шаблоны ответов для частых вопросов. Автоматическое распределение тикетов на наименее загруженного сотрудника. SLA-таймеры: если тикет не обработан в течение N часов — эскалация на старшего сотрудника.

### 9.6. Логирование действий

**REQ-SUP-003:** Все действия сотрудников логируются в `audit_logs`: изменение баланса, одобрение/отклонение вывода, решение по спору, одобрение/отклонение товара, бан пользователя или продавца.

## 13. Модуль Автоматизации Пробива {#13}

### 13.1. Обзор

**REQ-AUTO-001:** Модуль Автоматизации — это отдельный FastAPI-микросервис, развёрнутый независимо от основного бота. Он принимает задачи от основного бота, выполняет их автоматически через внешние API или распределяет между ручными воркерами, и возвращает результаты.

**Адрес сервиса:** `http://automation-service:8001`

### 13.2. Архитектура

```
Newlookup Bot → [POST /tasks] → Automation API
                                    ↓
                             automation_tasks (DB)
                                    ↓
                    ┌───────────────┴───────────────┐
                    ↓                               ↓
           Автоматический путь              Ручной путь
           (Celery Worker)                  (CRM для воркеров)
                    ↓                               ↓
         Внешние API:                      SearchBug / EmailRep
         - КС: csbot.service               (через браузер + прокси)
         - Телефон: Numverify                       ↓
         - Адрес: Smarty                   Воркер вносит результат
         - Email: EmailRep API                      ↓
                    ↓                       automation_tasks (DB)
         automation_tasks (DB)
                    ↓
         Newlookup Bot ← [GET /tasks/{id}] ← Automation API
                    ↓
         Закреплённое сообщение + .txt/.csv файл → Пользователь
```

### 13.3. Типы автоматизаций

| Тип | Метод | Сервис | Цена за запрос |
| :--- | :--- | :--- | :--- |
| **Кредитный скор (КС)** | Автоматический | `csbot.service` на `193.221.200.87` | Фиксированная |
| **Пробив номера** | Автоматический | Numverify API → Twilio Lookup (опционально) | ~$0.001–$0.005 |
| **Пробив адреса** | Автоматический | Smarty API | ~$0.004 |
| **Пробив email** | Автоматический | EmailRep API | Бесплатно до 250/день |
| **People Search** | Ручной (воркер) | SearchBug (личный кабинет) | Оплата аккаунта |

### 13.4. API эндпоинты Модуля

```
POST /tasks          — Создать задачу
GET  /tasks/{id}     — Получить статус и результат задачи
GET  /tasks          — Список задач (для Admin Panel)
POST /tasks/{id}/result — Воркер вносит результат (ручной путь)
GET  /workers        — Список воркеров CRM
GET  /accounts       — Список аккаунтов SearchBug
POST /accounts/{id}/ban — Пометить аккаунт как забаненный
```

### 13.5. Логика выполнения задачи

**Автоматический путь:**

1.  Основной бот создаёт задачу: `POST /tasks` с `service_type` и `input_data`.
2.  Celery Worker берёт задачу из очереди.
3.  Выполняет запрос к внешнему API.
4.  Записывает результат в `automation_tasks`.
5.  Основной бот периодически опрашивает статус: `GET /tasks/{id}`.
6.  При статусе `completed` — отправляет результат пользователю + закрепляет сообщение.

**Ручной путь (SearchBug):**

1.  Задача создаётся со статусом `manual`.
2.  В CRM-интерфейсе появляется новая задача.
3.  Воркер берёт задачу, видит входные данные.
4.  Открывает SearchBug через свой браузер с прокси.
5.  Выполняет поиск, копирует результат в CRM.
6.  Нажимает "Готово" → статус задачи меняется на `completed`.
7.  Основной бот получает результат и отправляет пользователю.

**Статус "В работе" для пользователя:**

Пока задача выполняется, пользователь видит сообщение:

```
⏳ Ваш заказ #12345 в обработке...
Тип: People Search
Ожидаемое время: ~20 минут
Статус обновляется автоматически.
```

### 13.6. CRM для ручных воркеров

**REQ-AUTO-002:** Простой веб-интерфейс (FastAPI + Jinja2), доступный воркерам по логину/паролю.

### 18.5. CC (Кредитные Карты от Продавцов)

Продавец сначала выбирает тип карты, затем загружает `.txt` файл. Система проверяет каждую строку по BIN (первые 6–8 цифр) и количеству полей.

| Подтип | Формат строки | Описание |
| :--- | :--- | :--- |
| `with_fullz` | `card;exp_month;exp_year;cvv;zip;name;address;ssn;dob;phone` | Карта с полными данными. |
| `zip_only` | `card;exp_month;exp_year;cvv;zip` | Карта только с ZIP. |
| `non_vbv` | `card;exp_month;exp_year;cvv` | Карта без VBV-проверки. |

**Проверка при загрузке:**

1.  Продавец выбирает тип (`with_fullz` / `zip_only` / `non_vbv`).
2.  Загружает `.txt` файл.
3.  Система проверяет каждую строку: соответствие формату по количеству полей.
4.  BIN-проверка: первые 6–8 цифр карты сверяются с базой BIN для определения банка и типа карты (debit/credit, prepaid, страна).
5.  Строки с ошибками отображаются в отчёте о загрузке.
